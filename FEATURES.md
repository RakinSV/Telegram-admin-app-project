# Бэклог фич — Telegram Content Repost System

> Приоритет: `P0` = без этого не MVP, `P1` = сразу после MVP, `P2` = рост и
> монетизация, `P3` = идеи на будущее, не блокируют ничего.
> Каждая фича — отдельная задача для Claude Code, можно брать по порядку.
>
> **Статус фичи живёт В ЗАГОЛОВКЕ**, а не в теле раздела: `РЕАЛИЗОВАНО`,
> `ЗАКРЫТО через FXX`, `ПРОПУЩЕНО`, `идея, не задача`. Так «что не сделано»
> проверяется одной командой и не врёт:
>
> ```
> grep -E "^### F[0-9]+" FEATURES.md | grep -viE "РЕАЛИЗОВАНО|ЗАКРЫТО|ПРОПУЩЕНО|идея, не задача"
> ```
>
> До 2026-08-08 у F01–F23 статус лежал в теле, и эта проверка показывала
> реализованные фичи как незакрытые — риск, что новая сессия начнёт
> переделывать готовое. **Помечай статус тем же коммитом, что и код.**
>
> **2026-08-15 — цель проекта расширена владельцем.** Было: «личный
> инструмент на много групп». Стало: **один продукт, закрывающий все
> Telegram-задачи — ведение групп, ботов и бизнес-обвязку, и для бизнеса,
> и для личного использования.** Из-за этого:
>
> - добавлены разделы **P5** (F52–F62, заимствования из разведки рынка) и
>   **P6** (F63–F74, бизнес-обвязка);
> - **F37** переоткрыта — решение «пропустить роли» принималось под старую
>   цель и под новой больше не годится;
> - **F49** переписана: строим поверх Telegram Stars (0% комиссии), а не
>   поверх стороннего платёжного сервиса;
> - **F27** привязана к развилке А/Б (см. преамбулу P6) — от неё зависит,
>   закладывать ли multi-tenant в схему БД сейчас или никогда.
>
> Источник P5 и P6 — разбор 53 конкурирующих продуктов, август 2026.
> Таблицы: `Telegram-анализ-рынка-v2.xlsx` (рынок) и
> `Telegram-реализация-сравнение.xlsx` (наш код против конкурентов,
> с колонкой «проверено по коду» у каждой строки).
>
> На 2026-08-08 из F01–F51 не реализованы ровно две: **F27** (SaaS
> multi-tenant) и **F39** (кросспостинг). Всё из P5 и P6 — не начато.

## P0 — ядро MVP

### F01 — Управление источниками (РЕАЛИЗОВАНО)
Добавление/удаление/просмотр списка отслеживаемых Telegram-каналов.
Хранение в таблице `sources` (id, channel_username, channel_title, is_active,
added_at). Интерфейс — минимум CLI-команды, в идеале — Telegram-бот команды
(`/add_source @channel`, `/list_sources`, `/remove_source @channel`).

### F02 — Telethon listener (РЕАЛИЗОВАНО)
Подключение к Telegram через Telethon (юзер-сессия), подписка на новые
сообщения в источниках из `sources`. При получении нового поста — запись в
таблицу `posts` со статусом `new`, сохранение текста, медиа (путь к файлу),
ссылки на оригинал, timestamp.

### F03 — Фильтрация по ключевым словам (РЕАЛИЗОВАНО)
Опциональные списки стоп-слов и обязательных слов на канал или глобально.
Применяется сразу при получении поста, до сохранения в очередь (либо
сохраняется со статусом `filtered_out` для прозрачности — лучше второе,
чтобы видеть, что отфильтровалось и почему).

### F04 — Дедупликация (базовая, хэш) — РЕАЛИЗОВАНО
Хэш текста поста (нормализованный — без пробелов/регистра) для отсева точных
дублей между источниками. Простая и быстрая первая линия защиты, до
семантического дубль-чека из P1.

### F05 — Очередь постов (статус-машина) — РЕАЛИЗОВАНО
Таблица `posts` со статусами: `new → filtered_out | duplicate | rewriting →
rewritten → pending_approval → approved | rejected → posted | failed`.
Чёткие переходы, логирование каждой смены статуса с timestamp.

### F06 — Рерайт через OpenAI-совместимое API (РЕАЛИЗОВАНО)
Клиент с конфигурируемым `base_url`/`api_key`/`model`. Промпт-шаблон
(хранится в файле/БД, не хардкод) с инструкцией на уникализацию текста
с сохранением смысла. Сохранение результата в `posts.rewritten_text`.
Логирование стоимости запроса (токены) в БД для последующего учёта расходов.

### F07 — Ручное одобрение через Telegram-бота (РЕАЛИЗОВАНО)
Бот в личке владельцу присылает рерайченный пост с inline-кнопками
✅ Одобрить / ❌ Отклонить / ✏️ Редактировать. При "Редактировать" — бот
просит прислать новый текст, заменяет `rewritten_text`. Статус меняется
соответственно нажатой кнопке.

### F08 — Публикация в группу (РЕАЛИЗОВАНО)
При статусе `approved` — публикация поста (текст + медиа, если есть) в
целевую группу через Telegram Bot API. Обновление статуса на `posted`,
сохранение `message_id` опубликованного поста и timestamp.

### F09 — Конфигурация через .env + pydantic Settings (РЕАЛИЗОВАНО)
Все параметры (telegram api_id/api_hash, session string, bot token, target
group id, openai-совместимые ключи) — через `.env`, валидация через pydantic.

### F10 — Базовое логирование и обработка ошибок (РЕАЛИЗОВАНО)
Структурированные логи всех этапов пайплайна (получен пост → отфильтрован/
прошёл → рерайчен → отправлен на модерацию → опубликован/отклонён). Retry
с экспоненциальной задержкой для сетевых вызовов (Telegram API, LLM API).

## P1 — сразу после MVP

### F11 — Авто-постинг по расписанию (РЕАЛИЗОВАНО)
APScheduler-джоба, которая публикует посты со статусом `approved` (или сразу
`rewritten`, если включён режим без модерации) по расписанию — например,
каждые N часов, либо в заданные временные слоты. Переключается флагом
`auto_post_enabled` в конфиге, не требует пересборки.

### F12 — Несколько целевых групп (РЕАЛИЗОВАНО)
Таблица `target_groups` (id, chat_id, title, is_active). Поле в `posts` или
отдельная таблица `post_targets` — какие посты в какие группы идут (может
быть all/subset). UI выбора через бот-команды или конфиг по умолчанию.

### F13 — Семантический дубль-чек (эмбеддинги) — РЕАЛИЗОВАНО
Замена/дополнение хэш-дедупликации (F04) на эмбеддинги через тот же
OpenAI-совместимый API. Косинусное сходство между новым постом и постами
за последние N дней. Порог схожести — конфигурируемый. Хранение векторов —
можно в SQLite как BLOB или через расширение sqlite-vec, без необходимости
поднимать отдельную векторную БД на этом масштабе.

### F14 — Статистика и логи (просмотры, реакции) — РЕАЛИЗОВАНО
Сбор `view_count`/реакций по опубликованным постам через Telegram API (если
бот — админ группы, либо период опроса через Telethon). Таблица
`post_stats` с историей по времени (для построения трендов). Команда бота
`/stats` — сводка за период.

### F15 — Стиль-профили рерайта (РЕАЛИЗОВАНО)
Несколько промпт-шаблонов под тип контента (новость/мнение/инструкция/юмор).
Либо ИИ сам классифицирует входящий пост перед рерайтом (отдельный лёгкий
запрос-классификатор), либо привязка стиля к конкретному источнику в
конфиге `sources`.

### F16 — Поиск дополнительных источников (идея пользователя) — РЕАЛИЗОВАНО
Интеграция с Brave Search API. По ключевым словам из оригинального поста —
поиск 5-10 результатов, фильтрация на релевантность (можно через тот же
LLM — "выбери 2-3 наиболее релевантных из списка"), разделение на
русскоязычные и англоязычные. Добавление блока "Источники:" в конец
рерайченного поста со ссылками. Включается опцией на источник или глобально
(галочка "добор знаний").

### F17 — Антибан-механики (РЕАЛИЗОВАНО)
Рандомизация задержек между запросами Telethon (не молотить API без пауз).
Лимиты на количество чтений/действий в час. Конфигурируемые джиттер-интервалы.
Это must-have для стабильности, не просто "nice to have" — без этого юзер-
сессия рискует попасть под ограничения.

### F28 — Guardian настраивается по целевым группам (РЕАЛИЗОВАНО)
Галочка «использовать Guardian» стоит на каждой `TargetGroup` в `/targets`,
список защищаемых чатов синхронизируется в `guardian.bot_config`
(`protected_chat_ids`), и все хендлеры/джобы/антирейд работают по СПИСКУ
чатов, а не по одному. `GUARDIAN_GROUP_ID` остался только ради одноразовой
миграции старых данных. Guardian отдельно проверяет, реально ли он может
модерировать чат (`guardian_can_moderate`): владелец мог отметить цель, но
забыть выдать боту права администратора.

Исходная постановка (для истории): Guardian был жёстко
привязан к ОДНОЙ группе через `GUARDIAN_GROUP_ID` в `.env` — при этом
`target_groups` (F12) поддерживает несколько целей публикации. Если целей
несколько, Guardian реально защищал только одну из них. Нужна была галочка
"использовать Guardian" на каждой `TargetGroup` в `/targets`, и Guardian
должен уметь обслуживать N групп одновременно (один бот, несколько чатов —
не N ботов). Требует ревизии схемы Guardian (`members`/`warnings`/
`banned_users` и т.д. сейчас неявно на одну группу, нужен `chat_id` как
часть ключа везде) до реализации — см. отдельный анализ перед стартом.
Найдено на аудите ведения групп (2026-07-17), запрошено пользователем явно.

## P2 — рост и монетизация

### F18 — Авто-обложки для постов (РЕАЛИЗОВАНО)
Если у поста нет медиа — генерация изображения. Два пути: (а) через
локальный ComfyUI (у пользователя уже настроен ComfyUI + ZLUDA на RX 6600 в
других проектах — можно переиспользовать инфраструктуру) или (б) через
Unsplash API по ключевым словам темы поста (бесплатно, быстрее, но не
уникально). Конфигурируемый выбор стратегии.

### F19 — Умное расписание публикаций (РЕАЛИЗОВАНО)
На основе накопленной статистики (F14) — анализ, в какое время аудитория
активнее всего (по просмотрам в первый час после публикации). Автоматический
сдвиг времени публикации под пиковые часы. Нужно minimum 2-3 недели данных
перед тем как это включать осмысленно.

### F20 — Авто-дайджест (РЕАЛИЗОВАНО)
Раз в неделю (или другой период) — джоба, которая выбирает топ-N постов по
просмотрам/реакциям за период и собирает их в один сводный пост через LLM.
Публикуется отдельно от обычного потока.

### F21 — Нативная реклама в ленте (РЕАЛИЗОВАНО)
Каждый N-й пост (конфигурируемо) — рекламный, ИИ вписывает рекламный текст
органично в формат канала по заданному брифу. Ручное добавление рекламных
брифов через бота, статистика отдельно по рекламным постам.

### F22 — Growth-трекер (РЕАЛИЗОВАНО)
Корреляция прироста подписчиков канала (нужен сбор через Telegram API или
сторонние боты-аналитики типа TGStat API) с типом/источником постов.
Отчёт "что реально растит канал".

### F23 — Веб-UI поверх системы (шаг к SaaS) — РЕАЛИЗОВАНО
Простой веб-интерфейс (FastAPI + минимальный фронт, либо Streamlit для
быстрого старта — у пользователя уже есть опыт со Streamlit из проекта
Hedonism Wines) для управления источниками, очередью модерации, статистикой
без необходимости лезть в бота или БД напрямую. Это шаг к продукту, который
можно продавать другим владельцам каналов.

### F29 — Управление уже опубликованным постом (РЕАЛИЗОВАНО 2026-07-18)
Сейчас редактирование (`/moderation/{id}/edit`) работает только ДО публикации
(пока пост в очереди модерации). После `posted` пост неприкасаем из
админки — нельзя ни поправить текст (Bot API `edit_message_text`/
`edit_message_caption`), ни удалить (`delete_message`), ни закрепить/
открепить (`pin_chat_message`/`unpin_chat_message`). Частый сценарий
владельца канала: заметил опечатку/фактическую ошибку уже после публикации.

Реализовано веб-only (без кнопок в Telegram-боте — список из N целей на
пост неудобно рисовать inline-клавиатурой): новая таблица `PostTarget`
хранит результат публикации КАЖДОЙ цели (не только первой успешной, как
раньше), `/moderation/{id}` показывает список целей с кнопками
редактировать/удалить/закрепить-открепить по каждой отдельно.

### F30 — Модерация комментариев под постами канала (ЗАКРЫТО через F28)
Discussion-группа канала, куда Telegram зеркалит комментарии под постами —
это ОБЫЧНАЯ supergroup с точки зрения Bot API, Guardian её никак не
отличает от любой другой защищаемой группы. После F28 (Guardian настраивается
по целевым группам, не глобально) владельцу достаточно добавить
discussion-группу как цель (`/targets`) и включить галочку Guardian на ней —
капча/антиспам/варны/антирейд начинают работать над комментариями без
дополнительного кода. Отдельная реализация не нужна.

Также закрывает F36 (приветствие новых подписчиков канала) — единственный
реальный механизм приветствовать "подписавшегося" описан именно через эту
discussion-группу (см. F36 ниже), это тот же путь.

### F31 — Полный сбор метрик поста (реакции, форварды) (РЕАЛИЗОВАНО 2026-07-18)
`PostStat` в БД уже поддерживает `reaction_count`/`forward_count`, но
собирается сейчас только `view_count` (`scheduler/stats.py`). Реакции и
форварды физически доступны через Bot API/Telethon, просто не читаются.

Сбор теперь идёт по ВСЕМ целям публикации поста (через `PostTarget`, F29),
не только по первой, и суммируется в один `PostStat`-снимок на пост.

### F32 — Управление инвайт-ссылками и заявками на вступление (РЕАЛИЗОВАНО 2026-07-18)
Создание/отзыв/лимиты по инвайт-ссылкам целевых групп, одобрение/отклонение
заявок на вступление (join requests, если у группы включено подтверждение
администратором) — сейчас полностью вне системы, только руками в самом
Telegram.

Веб-страница `/invites`: создание/отзыв инвайт-ссылок (`InviteLink`),
список pending-заявок с кнопками одобрить/отклонить. Заявки также
дублируются владельцу в личку ботом с теми же кнопками (см.
`telegram/moderation_bot.py::_on_chat_join_request`).

## P3 — идеи на будущее (не блокируют разработку)

### F24 — Сравнение версий источников (РЕАЛИЗОВАНО)
Если источники на разных языках расходятся в трактовке темы — пометка поста
«есть разные версии события».

Реализовано в `enrichment/enricher.py::compare_source_versions` (промпт
`prompts/compare_sources.txt`): отдельный LLM-вызов, срабатывает ТОЛЬКО когда в
доборе (F16) нашлись источники обоих языков и включена настройка
`version_comparison_enabled` (по умолчанию выключена — это лишний платный
вызов). При расхождении в начало блока источников добавляется строка
«⚠️ Разные версии события: …».

### F25 — Авто-реакция на жалобы/негатив (РЕАЛИЗОВАНО)
Мониторинг негативных реакций на опубликованный пост, уведомление при
превышении порога, опциональное авто-удаление.

Реализовано в `scheduler/stats.py`: подсчёт негативных реакций при опросе
статистики, порог и авто-удаление настраиваются в /settings → «Реакция на
негатив», есть почасовой лимит авто-удалений (`max_auto_deletes_per_hour`),
чтобы всплеск негатива не выкосил ленту.

### F26 — Ротация между несколькими Telethon-сессиями (РЕАЛИЗОВАНО)
Балансировка чтения между несколькими юзер-сессиями — масштабирование числа
источников без риска для одного аккаунта.

Реализовано в `telegram/listener.py`: дополнительные клиенты поднимаются по
сохранённым сессиям (`TelethonSession`, страница /telethon-sessions), источники
распределяются между ними по кругу, у КАЖДОГО аккаунта свой почасовой лимит
«тяжёлых» действий (F17/F26). Общий прокси на все клиенты (см. `proxy.py`).

### F27 — SaaS multi-tenant архитектура (ОСТАВЛЕН ОТКРЫТЫМ ОСОЗНАННО 2026-08-16)

> **Владелец решил не решать** — и это решение, а не забывчивость.
> Практическая разница на сегодня нулевая: страховка уже куплена там, где
> стоила копейки (`tenant_id` в 10 таблицах P6), а всё остальное в Б —
> биллинг, тарифы, изоляция Guardian на арендатора, Postgres — не пишется
> «на всякий случай».
>
> **Что это значит для работы:** правило про `tenant_id` в новых таблицах
> ОСТАЁТСЯ в силе (см. `CLAUDE.md`). Проектировать под Б не надо, но и
> закрывать дорогу нельзя.
>
> **Цена перехода на 2026-08-16, если Б однажды выберут:** 28 таблиц ядра
> без `tenant_id`, ревизия каждого запроса, отдельная БД Guardian на
> арендатора (сейчас она одна и это единственная граница безопасности),
> Postgres, тарифы, биллинг. Число таблиц растёт — значит цена тоже.
Полноценный переход от "система для одного владельца" к multi-tenant
продукту с отдельными аккаунтами, биллингом, изоляцией данных между
клиентами. Это отдельный по объёму проект поверх текущего ядра, не задача

### F33 — Опросы (polls) в ленте (РЕАЛИЗОВАНО 2026-07-18)

### F37 — Роли администраторов веб-панели (РЕАЛИЗОВАНО 2026-08-15)

⚠️ **МЕНЯЕТСЯ СПОСОБ ВХОДА.** Раньше вход был по одному паролю без имени.
Существующая учётка получает имя **owner** и роль **owner**; пароль прежний.
Пока пользователь в системе один, имя можно не вводить — иначе обновление
сломало бы вход тем, кто ставил систему до ролей.

**Три роли, строго вложенные:** `owner` (всё, включая секреты и настройки),
`editor` (контент и модерация), `analyst` (только чтение статистики).
Граница между владельцем и остальными проходит по секретам не случайно: у
нас это токены ботов и session string, то есть полный доступ к
Telegram-аккаунту, а не к контенту.

**ЗАПРЕТ ПО УМОЛЧАНИЮ — главное свойство.** Путь, не описанный в политике,
доступен ТОЛЬКО владельцу. Страница, добавленная через полгода и забытая в
`access.py`, не окажется открытой редактору: худшее, что произойдёт, —
сотрудник упрётся в отказ и спросит. Обратный порядок однажды тихо откроет
ему страницу секретов.

**Проверка — одним middleware, а не зависимостью роутера.** Зависимость надо
не забыть добавить к новому роутеру, и забытая она означает страницу вообще
без проверки прав. Middleware пропустить нельзя — это разница между «мы
стараемся проверять» и «проверка есть».

**Последнего владельца удалить нельзя.** Система без владельца — это система,
куда некому войти за настройками, и выбраться из этого через интерфейс
невозможно: страницу пользователей тоже открывает только владелец.

Мелочи: имя приводится к нижнему регистру; при неизвестном имени пароль всё
равно сверяется с фиктивным хэшем, иначе разница во времени ответа выдаёт,
какие имена заведены; роль из формы проверяется по списку — учётка с
неизвестной ролью не прошла бы никуда, то есть доступ сломался бы молча.

Миграция `0038_admin_roles`. Тесты: 25 на политику + 18 на живые роуты.
Запрет по умолчанию проверен на осмысленность: при замене на разрешение
падают ровно два теста.

### Исходная постановка F37 (для истории)
Сейчас один пароль на всю систему (`admin_users` — таблица физически на
одну строку). Ограничение записано прямо в докстринге `webui/auth.py`:
«Один администратор».

Решено с пользователем 2026-07-18: пропустить целиком для этого захода —
однопользовательский инструмент, ролевая модель не нужна прямо сейчас.

**ПЕРЕОТКРЫТО 2026-08-15.** То решение принималось под цель «личный
инструмент». Под новой целью (продукт для бизнеса) оно не работает:
пригласить редактора или SMM-щика, не отдав ему заодно все секреты и
настройки, физически нельзя — а секреты у нас это токены ботов и
session string, то есть полный доступ к аккаунту.

Роли минимум три: **владелец** (всё, включая секреты), **редактор**
(контент и модерация, без настроек и секретов), **аналитик** (только
чтение статистики). Блокирует F72 — контент-календарь с согласованием
без ролей бессмыслен.

### F39 — Кросспостинг на другие платформы (ОТКЛОНЁН 2026-08-16)

> **Решение владельца: только Telegram.** Сначала фича была принята с

Брать только если это личная потребность владельца. Как продуктовое
отличие — не работает.

### F40 — Редакция из двух агентов: профессиональный рерайт (РЕАЛИЗОВАНО 2026-08-01)
Раньше рерайт был «в один присест»: модель писала пост начисто, никто его не
правил — отсюда слабый, местами выдуманный текст. Теперь тот же клиент играет
ДВЕ роли (`rewriter/editorial.py`):

1. **Журналист** пишет черновик по источникам (персона усилена: журналист с
   20-летним опытом).
2. **Редактор-фактчекер** сверяет черновик с источниками (исходный пост +
   статья по ссылке), пишет пронумерованные замечания и вердикт OK/ПРАВИТЬ,
   помечает спорные факты на веб-сверку.
3. **Веб-сверка** помеченных фактов через тот же поиск, что F16 (SearXNG/
   Brave); находки идут журналисту.
4. **Журналист переписывает** по замечаниям и находкам. Цикл — до вердикта OK
   или до `editorial_max_rounds`.

Замечания редактора сохраняются на варианте (`PostRewriteVariant.editorial_notes`,
миграция 0023) и показываются при модерации. По умолчанию ВКЛ, 1 раунд; всё —
настройками в /settings → «Редакция из двух агентов». Дороже по токенам: 1 раунд
= 3 вызова LLM на вариант, поэтому под выключателем. 402/ошибка баланса на любом
шаге останавливает пачку (посты остаются `new`); прочие сбои рецензии/правки не
теряют хороший черновик.

## P4 — Вовлечение аудитории: боты-помощники админа (F41–F49)

Запрос владельца 2026-08-01: нужны дополнительные обслуживающие боты —
геймификация, приглашения с указанием источника рекламы, конкурсы, «и что там
ещё надо админам групп». Ниже — результат разбора, что реально нужно и что
физически позволяет Telegram Bot API.

### Архитектурное решение: куда что класть

Три процесса вместо двух, с чётким разделением по СОБЕСЕДНИКУ:

| Процесс | С кем говорит | Зона ответственности |
|---|---|---|
| Репост-бот (есть) | владелец | публикация, модерация контента |
| Guardian (есть) | группа | защита: капча, антиспам, варны, антирейд |
| **Engage (новый)** | **участники** | квизы, конкурсы, рефералы, предложка, онбординг |

**Итого три бота.** Разделены по СОБЕСЕДНИКУ, а не по фичам — это и есть
причина, по которой третий бот действительно нужен, а не «ещё один процесс ради
процесса»:

- Репост-бот — приватный инструмент владельца (кнопки одобрения постов, статистика).
- Guardian — «полицейский» в группе, участники с ним не разговаривают.
- Engage — публичный, дружелюбный: участники пишут ЕМУ в личку, deep-link
  рефералки ведёт на НЕГО, он же ведёт квизы и конкурсы. Смешивать его с
  «ботом владельца» — плохой UX (подписчик видит чужие админ-кнопки) и лишняя
  поверхность атаки.

**Важно: Engage НЕ читает поток сообщений группы.** Ему это не нужно — квиз
работает по схеме «бот спросил → участник нажал кнопку → `poll_answer`».
Значит, не нужен privacy mode off, не нужно дублировать трафик Guardian'а и не
растут риски по лимитам Telegram. Это следствие правильно выбранной механики
(см. F43): если бы очки давались за сообщения, второй читатель потока был бы
неизбежен.

### Что Telegram реально позволяет (сверено с Bot API)

- **`ChatMemberUpdated.invite_link`** и **`ChatJoinRequest.invite_link`** — при
  вступлении Telegram САМ сообщает, по какой ссылке пришёл человек. **Эти данные
  нам уже приходят в существующие хендлеры, но мы их не сохраняем** — отсюда F41,
  самая дешёвая и самая полезная фича блока.
- **Deep-link `t.me/<bot>?start=<payload>`** (payload до 64 символов) — основа
  реферальной программы: по нему бот узнаёт, кто пригласил.
- **`getChatMember(chat_id, user_id)`** — проверка «подписан ли» для условий
  конкурса. Требует, чтобы бот был админом в проверяемом чате.
- **`sendDice`** — нативный рандом Telegram (кубик/дартс), годится для
  наглядного публичного розыгрыша «на глазах у зрителей».
- **Ограничение:** в КАНАЛАХ у постов нет авторов-участников — бот не видит, кто
  что написал. Геймификация по активности работает только в ГРУППАХ, включая
  discussion-группу канала (что для канала и есть рабочий вариант).
- **Нет события «подписался на канал»** — у ботов такого апдейта не существует
  (уже упиралось в F36). Прирост канала считаем по `getChatMemberCount`, а
  поимённо — только по вступлениям в группу.

### F41 — Атрибуция подписчиков: откуда пришёл (РЕАЛИЗОВАНО 2026-08-06)
Продолжение F32. Сейчас инвайт-ссылки создаются и отзываются, но **никто не
знает, какая из них сколько привела** — данные от Telegram выбрасываются.

Сохранять `invite_link` при вступлении (`chat_member`) и в заявке
(`chat_join_request`) → поле в `JoinRequestRecord` + новая таблица
`MemberOrigin` (chat_id, user_id, invite_link_id, joined_at, left_at).
На `/invites` — колонки «пришло / осталось сейчас / отвалилось / retention 7д и
30д». Плюс поле «стоимость размещения» у ссылки → **CPA, цена подписчика**.

Это замыкает контур с F35 (учёт рекламного дохода) с другой стороны: F35 — что
заработали на рекламе у себя, F41 — что потратили на рекламу себя и что это
принесло.

### F42 — Реферальная программа для участников (РЕАЛИЗОВАНО 2026-08-06, ПОЧИНЕНО 2026-08-16)

> **Не работала три месяца, и об этом стоит помнить.** Антифрод требует трёх
> условий: вступил, написал, прожил N дней. Условия «вступил» и «написал»
> выставлять было НЕКОМУ — `mark_joined` и `mark_first_message` не
> вызывались ниоткуда. Значит ни один реферал не подтвердился ни разу, очки
> не начислялись, а F67 (комиссия партнёру) не мог заработать в принципе:
> он требует подтверждённого реферала.
>
> Отметки повешены на Guardian: он единственный видит и вступления, и
> сообщения в группе. Первое сообщение засчитывается ПОСЛЕ детерминированных
> фильтров — иначе условие обходилось бы одним спам-сообщением.
>
> Почему не поймали раньше: у каждой функции были свои зелёные тесты, и они
> сами вызывали то, что в бою не вызывалось. Сторож на будущее —
> `tests/test_referral_lifecycle.py` и `tests/test_feature_reachability.py`.
Участник пишет боту Engage → получает персональную ссылку
`t.me/<bot>?start=ref_<user_id>` (или персональную инвайт-ссылку группы) →
система считает, кого он привёл и кто из них остался. Лидерборд рефереров,
награды за пороги (N приглашённых → роль/бейдж/приз). Защита от накрутки:
приглашённый засчитывается только если прожил в группе > N дней и написал хотя
бы одно сообщение.

### F43 — Геймификация: контент → вопрос → очки (РЕАЛИЗОВАНО 2026-08-06)
**Механика владельца (уточнено 2026-08-01):** бот САМ выдаёт контент, а через
время задаёт по нему вопрос. Ответил верно — очки.

Это принципиально лучше «очков за сообщения»: те превращаются в ферму флуда
(люди пишут «+», «ок», чтобы набить счётчик), а здесь очки даются за то, что
человек реально прочитал материал. И механика самодостаточна: не требует, чтобы
в группе кто-то что-то писал — бот сам создаёт повод.

**Почему это ложится на нашу систему почти без работы:** у нас уже есть полный
текст статьи (trafilatura, F16), готовый пост и редактор-фактчекер (F40),
который эти факты проверил. Составить из проверенного материала вопрос с
вариантами ответа — ОДИН дополнительный LLM-вызов. Вопрос гарантированно
основан на реальном тексте, а не на выдумке модели.

Схема:
1. Пост опубликован обычным пайплайном.
2. **Составитель квиза** (новая LLM-роль) делает из статьи вопрос + 3–4 варианта
   ответа, один верный, плюс короткое пояснение со ссылкой на источник.
3. Через настраиваемую паузу бот Engage публикует вопрос в группу как
   **quiz-poll** (`sendPoll(type="quiz", correct_option_id=...)`).
4. Очки за правильный ответ, бонус за скорость и за серию дней.
5. Уровни/бейджи, `/me`, `/top` (день/неделя/месяц), авто-пост лидерборда.

**Почему quiz-poll, а не свободный ответ:** Telegram нативно поддерживает
викторину — сам проверяет правильность, показывает верный вариант с пояснением
и не даёт переголосовать. Это ноль LLM-вызовов на проверку ответов и ноль
споров «я вообще-то это и имел в виду». Свободные ответы с LLM-проверкой —
возможное расширение потом, но дороже и спорнее.

Очки начисляются также за приведённого реферала (F42) и участие в конкурсе
(F44). Настраивается на чат, выключается одной галочкой.

**Ограничение:** публиковать вопрос и видеть ответы бот может только в ГРУППЕ
(в канале нет участников-авторов) — для канала это его discussion-группа.

### F50 — «Редакционная кухня»: живая трансляция диалога агентов (РЕАЛИЗОВАНО 2026-08-06)
Запрос владельца 2026-08-01: «хочу видеть, что копирайтер с редактором
обсуждают и что переписывают».

**Что важно понимать про природу этих «ботов»:** журналист и редактор — не
отдельные Telegram-боты, а LLM-роли внутри одного процесса
(`rewriter/editorial.py`), они не «переписываются», а вызываются
последовательно. Делать из них настоящих ботов, которые шлют друг другу
сообщения через Telegram, — это добавить сетевые задержки, лимиты и точки
отказа ради театральности. **Но показать их обмен как живой диалог — можно и
нужно, и это почти бесплатно:** мы просто транслируем то, что и так происходит.

Как это выглядит: отдельный чат «редакционная кухня» (приватная группа или
канал — только для владельца), куда по каждому посту приходит цепочка,
связанная реплаями:

```
📝 Журналист · пост #123 · черновик
   [текст черновика]
   └ 🔍 Редактор · ВЕРДИКТ: ПРАВИТЬ, 3 замечания
        1. Выдумана цифра «50% рынка» — в источниках её нет
        2. Слабый лид: начинается с «в последнее время»
        3. Не убрана ссылка на канал автора
      └ 🌐 Проверка фактов · сверено 2 утверждения
           • «крупнейший банк 2025» → расходится, см. example.com/a
        └ ✍️ Журналист · правка готова
             [итоговый текст]
          └ ✅ Редактор · одобрено. 1 раунд, 4 200 токенов
```

**Техническое решение (важно для чистоты слоёв):** `rewriter/editorial.py` НЕ
должен ничего знать про Telegram — сейчас он не импортирует ни бота, ни БД, и
это стоит сохранить. Поэтому в `editorial_rewrite()` добавляется необязательный
callback `on_step(stage, text)`, а связывает его с ботом уже
`scheduler/jobs.py`. Тогда та же трансляция без переделок уходит и в веб-панель
(SSE-поток `/logs` уже есть, см. `webui/log_broadcast.py`), и в тесты (callback
подменяется списком).

Отдельный бот НЕ нужен — шлёт существующий репост-бот.

Настройки:
- `editorial_newsroom_enabled` — включить трансляцию;
- `editorial_newsroom_chat_id` — куда (можно поставить свой user_id и получать
  в личку, но **не рекомендуется**: 4–5 сообщений на пост забьют ту же личку,
  где кнопки одобрения);
- `editorial_newsroom_verbosity` — `all` (весь ход) / `problems` (только когда
  редактор нашёл замечания) / `summary` (одна строка-итог на пост).

**Предупреждение по объёму:** при пачке в 5 постов за тик и `all` это ~25
сообщений за тик. Поэтому режим по умолчанию — `problems`: молчит, когда всё
хорошо, и показывает разбор, когда редактор реально что-то нашёл. Длинные
тексты режутся существующим `_clip` (UTF-16-корректная обрезка под лимит
Telegram 4096).

**Зачем это на самом деле нужно** (не только «интересно посмотреть»): это
инструмент отладки качества. Когда рерайт выходит плохим, сейчас видно только
результат — а причина может быть в чём угодно: статья не скачалась, редактор
придрался не к тому, промпт кривой. Живой ход разговора показывает, на каком
шаге всё пошло не так, и позволяет чинить конкретный промпт, а не гадать.

### F49 — Платный доступ и подписка (ЯДРО ГОТОВО 2026-08-16, НЕ ПРОВЕРЕНО ЖИВЫМИ ПЛАТЕЖАМИ)

> ⚠️ **Статус честный, а не «реализовано».** Написаны и покрыты тестами
> журнал операций, выдача и снятие доступа, обработчики счёта и оплаты.
> **Ни один сценарий не прогонялся против настоящего Telegram** — для этого
> нужен бот, подписка и настоящие звёзды. Поведение платёжного API взято из
> документации.

**ЖУРНАЛ ФАКТОВ ВМЕСТО ПОЛЯ СОСТОЯНИЯ** (`payment_events`, append-only).
Оплата приходит апдейтом, апдейт может продублироваться: переподключение,
ретрай, перезапуск бота с недоставленной очередью. «Выдать доступ, если
статус не активен» на повторе выдаст его дважды и продлит срок бесплатно.
Каждый факт сначала пишется в журнал, и только НОВЫЙ факт что-то меняет.

**Ключ идемпотентности — `(kind, charge_id, period_end)`,** и это осознанный
компромисс при непроверенном поведении Telegram: достоверно неизвестно,
выдаёт ли продление новый `telegram_payment_charge_id` или повторяет
прежний. Ключ из трёх полей верен в обоих случаях. `period_end` NOT NULL,
потому что в SQL уникальность не срабатывает на NULL — разовые платежи
дублировались бы беспрепятственно.

**Порядок «сначала запись, потом выдача».** Упасть после выдачи ссылки хуже,
чем после записи: повтор апдейта выдаст вторую ссылку, а оплата без ссылки
чинится кнопкой «моя ссылка».

**Ссылка персональная, `member_limit=1`.** Общая означала бы, что один
оплативший приводит весь чат.

**Кик — это бан + снятие бана.** Бан без снятия оставляет человека в чёрном
списке: он оплатит снова и не сможет войти. Обратная дорога — весь смысл
подписки.

**Запас в 6 часов перед закрытием.** Продление приходит отдельным апдейтом и
может опоздать; выкинуть заплатившего и позвать обратно через пять минут
хуже, чем подождать.

**Срок берётся ИЗ ОТВЕТА Telegram, а не считается нами.** Период считает он,
и своя арифметика поверх рано или поздно разойдётся с тем, что человек
видит в интерфейсе Telegram.

Миграция `0043_payments`. Тестов 45. Настройки — `/settings` → «Платный
доступ (Stars)», по умолчанию ВЫКЛЮЧЕНО.

**Страница `/subscriptions`** — только владелец: здесь видна выручка и
отсюда делается возврат, это уровень секретов, а не редактора контента.
Выручка считается ПО ЖУРНАЛУ: сложить активные подписки значило бы потерять
и возвраты, и уже закончившиеся оплаты.

**Возврат (`refundStarPayment`) делает ТОТ ЖЕ БОТ, что принял оплату** —
метод привязан к токену. Веб-процесс поднимает Engage на один вызов, как в
ответах поддержки (F68). Порядок: сначала деньги, потом доступ. Отказ
Telegram означает, что денег человек не получил, и закрывать доступ в этот
момент нельзя — иначе он остаётся и без канала, и без денег. Снятие доступа
делается здесь же, а не джобой: та берёт только активные по сроку, а у
возвращённой подписки статус другой и срок ещё не вышел.

#### TON и USDT вместо звёзд — разобрано 2026-08-16, ответ «нет»

Вопрос владельца: можно ли принимать оплату подписки в TON или USDT через
кошелёк Telegram. Технически да — есть Wallet Pay, TON Connect и просто
перевод на адрес с проверкой в блокчейне. **Но именно для доступа в канал
это запрещено.**

Доступ к закрытому каналу — ЦИФРОВОЙ ТОВАР, а с 2024 года цифровые товары
в ботах и мини-аппах продаются ТОЛЬКО за Stars. Обход через любой другой
способ оплаты — основание для бана бота, то есть потери всей аудитории
разом. Это не про комиссию, а про право работать.

**При этом платить криптой человек может — и мы ничего не нарушаем.**
Звёзды покупаются в том числе за TON: с его стороны это оплата криптой, с
нашей — обычный платёж Stars. И деньги владелец тоже получает в TON: вывод
идёт через Fragment, доступен через 21 день после получения звезды.

**Где крипта законна и нужна — F70,** физические товары магазина (F69): на
них правило про Stars не распространяется, а вот на подписку и доступ —
распространяется.

Правила Telegram по платежам менялись несколько раз; **сверить перед
включением**, а не полагаться на эту запись.

**Осталось до боевого включения:**
- прогон на живом боте с настоящей подпиской и настоящими звёздами;
- сверить процент разработчика в ToS 6.2.4 (в разведке извлечь не удалось).

#### Исходная постановка
Монетизация закрытого канала: оплата через Telegram Stars → автовыдача
инвайт-ссылки с ограничением, авто-кик по окончании подписки, продление.
Отдельный крупный кусок с платёжным контуром и юридическими вопросами —
записано, чтобы не потерялось, но не в ближайшую очередь.

**Пересмотрено после разбора экономики рынка.** Ставка на Stars,

| Способ | Комиссия |
|---|---|
| **Telegram Stars** | **0%** — Telegram не берёт ничего |
| Bot Payments API | 0% Telegram + 2.8–3.9% провайдеру |
| Tribute | 10% |
| PaidSub.io | 15% |
| Paywall.pw | 20% |

Единственный вычет у Stars — 30% Apple/Google (15% при доходе <$1M/год),

Дополнительно: с 2024 Stars ОБЯЗАТЕЛЬНЫ для продажи цифровых товаров в

**Что делаем мы, а что Telegram.** Платёжный контур — Telegram (подписка
включается в настройках канала, автосписание каждые 30 дней, доступ

### F51 — Сюжеты: одна новость из нескольких источников (РЕАЛИЗОВАНО 2026-08-07)

**Проблема пользователя:** источников много, одна и та же новость приходит из
нескольких и публикуется повторно.

Отдельная «БД новостей» не понадобилась — она уже есть (`posts`). Не работали
два имеющихся слоя дедупа, каждый по своей причине:

1. **Дыра в RSS.** `rss/poller.py` считал `content_hash`, клал его в базу и
   НИ РАЗУ не сверял; семантического дубль-чека там не было вовсе.
   `_known_guids` её не закрывает — он сравнивает guid ВНУТРИ одной ленты.
   Для ИБ-новостей это било сильнее всего: одна CVE из пяти лент = пять
   постов и пять оплаченных рерайтов.
2. **Семантика была выключена** по умолчанию, а хэш ловит только буквальный
   копипаст: разные редакции пишут об одном событии своими словами.

**Решение — не заплатка.** Дыра появилась потому, что правила приёма
скопировали в две ветки и в RSS-копию половину проверок не перенесли. Приём
вынесен в `tg_repost/ingest.py`; у вызывающих осталось только то, что у них
действительно различается — чем опознаётся «уже видел это» (Telegram:
`message_id`, RSS: `guid` ленты).

**И смысл дубля перевёрнут.** Повтор из НЕЗАВИСИМОГО источника — не мусор, а
подтверждение: ровно на нём работает редактор-фактчекер (F40) и сравнение
версий (F24). Семантический повтор больше не исчезает, а цепляется к первому
пришедшему посту в сюжет (`story_clusters`). Публикуется по-прежнему один
пост; остальные живут при нём источниками и уходят в фактчек.

Буквальный копипаст по хэшу в сюжет НЕ идёт: считать его «вторым источником»
значило бы врать редакции о числе подтверждений.

**Настройки** (`/settings` → «Дубли и сюжеты»): семантика теперь ВКЛ по
умолчанию, порог 0.88 (было 0.92 — пропускал половину реальных повторов),
окно сравнения 3 дня, пауза на сбор сюжета `cluster_grace_minutes` (по
умолчанию 0 — это прямая задержка публикации, включать осознанно).

**Ограничения, про которые стоит помнить:**
- база сравнения наполняется постепенно: у постов, набранных при выключенной
  семантике, эмбеддинга нет, и первые дни повторы ещё будут проскакивать;
- в промпт уходит максимум 4 источника по 1500 символов — сюжет из десяти
  лент иначе раздул бы счёт за токены без пользы;
- `primary_post_id` намеренно без ForeignKey: пара FK с `posts.cluster_id`
  замкнула бы цикл, на котором падает `create_all` (SQLite не умеет
  `ALTER ... ADD CONSTRAINT`).

### Что НЕ вошло и почему
- **Приветствие подписчиков канала поимённо** — Bot API физически не даёт

### F53 — ERR (Engagement Rate by Reach) (РЕАЛИЗОВАНО 2026-08-15)
Подсмотрено у TGStat, где ERR — основа платных тарифов. Именно этой цифрой
рекламодатель торгуется за размещение.

Чистая формула поверх УЖЕ собранных просмотров (F14/F31) и подписчиков
(F22) — ни одного нового сбора данных.

**ДВЕ метрики, а не одна.** В отрасли «ERR» называют разные вещи: одни
считают охват к подписчикам, другие вовлечённость к охвату. Свести их в
одно поле значило бы отдавать рекламодателю число, смысл которого зависит
от того, кто его читает. Поэтому обе считаются отдельно и названы по
формуле: `reach_rate` = просмотры / подписчики, `engagement_rate` =
(реакции + пересылки) / просмотры. Точную формулу TGStat подтвердить не
удалось — сайт не открылся из-под текущего исходящего IP.

**Главная ловушка реализации.** `post_stats` хранит СНИМКИ во времени: у
поста, замеренного трижды, три строки — 100, 400 и 900 просмотров. Наивная
сумма превратила бы один пост с 900 просмотрами в 1400, завысив охват,
который потом покажут рекламодателю. Берётся только последний снимок.

**Найденный по дороге баг, общий для F14 и F53.** Отбор «последнего снимка»
через `ORDER BY captured_at DESC` недетерминирован: гранулярность системных
часов на Windows ~15 мс, поэтому два замера подряд регулярно получают
ОДИНАКОВУЮ метку, а при равенстве порядок строк не определён. Пойман
прогоном одного теста десять раз подряд: 4 прохода, 6 падений. Добавлен
тай-брейк по `id` — и здесь, и в `scheduler/stats.py::compute_stats_summary`
(F14), где та же ошибка жила с момента написания и могла отдавать
устаревший снимок в статистику.

Вывод: блок по каждому активному каналу в `/stats` (функция
`engagement_lines`, переиспользуется веб-страницей). Каналы без данных
пропускаются молча; неполное покрытие метриками показывается явно
(«метрики есть у 1 из 10 постов») — иначе владелец назовёт рекламодателю
среднее по одному посту, не зная об этом.

Тесты: 18 в `tests/test_engagement.py`, включая пять прогонов подряд на
детерминированность при совпадающих метках времени.

### F54 — Фильтры на уровне ИСТОЧНИКА (РЕАЛИЗОВАНО 2026-08-15)
Подсмотрено у RSS-to-Telegram-Bot: каждой ленте свои фильтры. Шумному
источнику строгие правила, спокойному мягкие.

**Это была одновременно фича и починка вранья в документации.** `README.md:216`
и `README.ru.md:215` обещали «стоп-/обязательные слова глобально или на
канал», а в модели `Source` не было ни одного такого поля. Теперь обещание
стало правдой, и тексты README править не пришлось — они описывали то, что
и должно было быть.

**АСИММЕТРИЯ ДВУХ СПИСКОВ — главное решение фичи.** Стоп-слова источника
СКЛАДЫВАЮТСЯ с глобальными, обязательные ЗАМЕЩАЮТ их. Выглядит
непоследовательно ровно до тех пор, пока не вспомнишь, как работает фильтр:

* стоп-слово отсекает пост при ЛЮБОМ совпадении → объединение делает
  правила строже. Позволить источнику молча отключить глобальную защиту
  опаснее, чем оставить лишнее ограничение;
* обязательные срабатывают по «ХОТЯ БЫ ОДНОМУ» → объединение не ужесточило
  бы фильтр, а ослабило: чем длиннее список, тем больше проходит.
  Замещение даёт ленте её собственную тему.

**Три состояния, а не два.** `NULL` — следовать глобальному списку, пустая
строка — явное «требования нет», непустая — свои слова. Для стоп-слов первые
два эквивалентны, для обязательных — принципиально разные. Текстовое поле
три состояния не выражает, поэтому в форме источника рядом стоит галочка
«переопределить глобальный список».

**Где применяется.** В `ingest.py` — точка одна для Telegram и RSS, второй
раз дыру как в F51 не открываем. Списки резолвятся и в `compute_embedding`:
если бы там остались только глобальные, экономия на платных эмбеддингах
перестала бы работать ровно для тех лент, ради которых фича и делалась.

**Отклонение от первоначальной записи:** здесь предлагалось взять схему из
Guardian (отдельная таблица `stop_words` с ключом `chat_id`). Сделано
колонками на `sources`: рядом уже лежат `target_chat_ids` (CSV) и
`style_profile` — переопределения источника хранятся именно так, и третий
способ хранить то же самое создал бы в системе два разных механизма.
Пер-чатовые списки Guardian (F28) остаются отдельной таблицей: они
редактируются командами бота и требуют аудита `added_by`, а эти — формой.

Миграция `0029_source_filters`. Тесты: 16 в `tests/test_source_filters.py`
плюс 3 роутовых. Асимметрия проверена на осмысленность: при подмене
семантики на противоположную падают ровно 5 тестов.

### F55 — Recycling: повтор выстреливших постов (РЕАЛИЗОВАНО 2026-08-15)
Подсмотрено у Publer (проверено в браузере) и Onlypult. Почти бесплатный
охват из уже проверенного контента: данные для отбора и так лежали в
метриках (F14/F31), не хватало только постановки повтора в очередь.

**Повтор идёт в МОДЕРАЦИЮ, а не в публикацию.** Создаётся
`Post(kind=RECYCLE, status=REWRITTEN)` — дальше обычный пайплайн, владелец
видит превью с пометкой **🔁 ПОВТОР** и жмёт «одобрить». Пометка не
косметика: без неё повтор выглядит как новый пост, владелец одобряет его не
глядя, и ручное подтверждение перестаёт быть подтверждением.

**Четыре правила отбора, каждое закрывает свой способ испортить ленту:**

1. **только `kind=SOURCE`** — иначе повтор сам стал бы кандидатом на
   следующем проходе и один и тот же текст крутился бы бесконечно. Самое
   важное правило файла: повтор — это опубликованный пост нужного возраста
   с просмотрами, то есть по всем прочим признакам идеальный кандидат;
2. **не повторять дважды** — наличие поста с `recycled_from_id == X`
   закрывает X навсегда. Отдельного флага не нужно, признаком служит сама
   связь. Работает и когда владелец повтор ОТКЛОНИЛ: отклонение означает
   «этот пост повторять не надо», возвращать его в кандидаты значило бы
   предлагать одно и то же на каждом проходе;
3. **минимальный возраст** — вчерашнее аудитория ещё помнит, и повтор
   читается как сбой, а не как напоминание;
4. **порог просмотров** — повторяем выстрелившее. Пост без единого снимка
   метрик считается за 0 просмотров и при любом положительном пороге не
   проходит: «не знаем, выстрелил ли» — не повод повторять.

**`content_hash` намеренно НЕ копируется** в повтор: он служит дедупликации
на приёме, и повтор с тем же хэшем был бы отсеян как «точный дубль» — фича
ломала бы сама себя. В приём повтор не заходит, но копия хэша сделала бы
будущую ошибку тихой.

Противоречивые настройки (`RECYCLE_MIN_AGE_DAYS >= RECYCLE_WINDOW_DAYS`)
дают предупреждение в лог: окно схлопывается, кандидатов не будет никогда, а
со стороны это выглядит как «фича не работает».

Миграция `0030_recycle` (самоссылка `posts.recycled_from_id`, без именованного
FK — SQLite не умеет `ALTER ADD CONSTRAINT`, тот же приём, что в 0028).
Настройки — группа «Повтор выстреливших постов» на `/settings`, обе локали.
Тесты: 22 в `tests/test_recycle.py`. Правило 1 проверено на осмысленность:
при снятии фильтра по `kind` падают ровно два теста про бесконечный цикл.

### F56 — MTProto-статистика канала (РЕАЛИЗОВАНО 2026-08-15, СКОУП СУЖЕН)

**Сделано.** Скалярные показатели `stats.getBroadcastStats` снимаются раз в
сутки в собственную историю (`channel_stats_snapshots`, миграция
`0031_channel_stats`): доля подписчиков с ВКЛЮЧЁННЫМИ уведомлениями плюс
средние просмотры/репосты/реакции от самого Telegram.

**Главное — `enabled_notifications`.** Её падение означает, что люди ещё
числятся подписчиками, но отключили звук и не читают: отток за неделю до
самой отписки. Никаким другим способом это не вычисляется. В `/stats`
выводится динамика, а при падении больше чем на 1 п.п. — предупреждение
«ТИХИЙ ОТТОК». Порог именно такой, потому что тревога по десятым долям
приучает не смотреть на предупреждения вообще.

**Числа подписчиков в новой таблице НЕТ намеренно** — его собирает F22, и
вторая колонка с тем же смыслом означала бы два источника правды, которые
рано или поздно разойдутся. `views_per_post` и прочие при этом НЕ дубль
наших метрик: F14/F31 считают по постам, которые опубликовали мы, а эти —
по всем постам канала, включая опубликованные вручную.

**Отсутствие прав администратора — отдельное состояние, не ошибка.** Оно
считается своим счётчиком и логируется отдельной строкой с указанием, что
делать. Сваленное в общий счётчик сбоев, оно выглядит как «что-то
сломалось» и живёт в логах годами.

`tenant_id` в новой таблице заложен сразу. Формально решение 1 писалось про
фазы 11–14, но довод («одна колонка сейчас против миграции по всей базе
потом») к любой новой таблице относится ровно так же.

**ЧТО НЕ ВОШЛО (осознанно, не забыто) — остаётся открытым:**
- **графики** (`growth_graph`, `mute_graph`, `top_hours_graph`): Telegram
  отдаёт их как `StatsGraphAsync` — токен, который надо догружать вторым
  вызовом `stats.loadAsyncGraph` и разбирать чужой JSON. Своя история из
  скалярных снимков даёт ту же динамику проще, ровно как в F22;
- **`stats.getMessagePublicForwards`** — кто репостнул пост, готовый список
  для взаимопиара. Отдельный вызов на каждое сообщение, то есть свой бюджет

- **мегагруппы** — у них метод `stats.getMegagroupStats` и другой набор

Тесты: 19 в `tests/test_channel_stats.py`. Изоляция: фикстура чистит ВСЕ
целевые каналы, потому что сборщик по своей природе обходит весь список —
поймано тем, что тесты проходили по отдельности и падали в общем прогоне.

### Исходная постановка F56 (для истории)  ⭐ ГЛАВНЫЙ РЫЧАГ
Официальный статистический API уровня MTProto — `stats.getBroadcastStats` и
`stats.getMessagePublicForwards` (core.telegram.org/api/stats). Греп
`getBroadcastStats`: 0 вхождений, не вызываем вообще.

Что даёт:
- **`mute_graph`** — кто отключил уведомления. Это отписка за неделю до
  самой отписки: человек ещё в подписчиках, но уже не читает.
- **`new_followers_by_source_graph`** — откуда пришли подписчики: поиск,
  ссылки, репосты. Дополняет F41, который знает только про наши инвайты.
- **публичные репосты поста** — какие каналы вас репостнули. Готовый список
  для взаимопиара по факту, а не по интуиции.

**Почему это рычаг, а не просто фича.** Bot API таких методов НЕ ИМЕЕТ —
конкурентам-ботам они недоступны в принципе, для них это стена. Нам нужна
юзер-сессия, и она у нас уже крутится в listener (F02). То есть данные
лежат на расстоянии одного вызова.

Требует прав администратора канала. Складывать в собственную историю —
Telegram отдаёт срез, а ценность в динамике.

### F57 — Петля обучения антиспама (РЕАЛИЗОВАНО 2026-08-15)

Спорные вердикты AI-фильтра уходят в лог-канал с кнопками «спам / не спам»,
решения копятся в `spam_reviews` (Guardian, миграция `0003_spam_reviews`) и
подмешиваются в промпт few-shot. Классификатор дообучается на ЭТОЙ
аудитории, где граница между спамом и своими шутками про заработок своя.

**Дыра, которую закрыли.** `ai_filter.classify` возвращал `None` при ошибке,
таймауте или битом JSON, и `_ai_check` молча пропускал сообщение. Решение
верное — лучше пропустить спам, чем удалить живого человека, — но обратной
связи не было вообще: фильтр ошибался и не узнавал об этом, владелец тоже.
Теперь на разметку идут ДВА случая: «классификатор не ответил» и «ответил
спам, но уверенности не хватило до порога». Второй ценнее: именно на этой
границе разметка двигает порог под конкретную аудиторию.

**Поведение модерации не изменилось.** F57 ничего не удаляет и не банит —
только наблюдает. Это записано и в коде, и в тестах.

**Два неочевидных решения:**

1. **Баланс примеров обязателен.** Размечать тянет прежде всего спам — он
   раздражает, его замечают. Сложи примеры как есть, и в промпт уедут
   двадцать спамов и один нормальный текст: модель научится ровно одному —
   называть спамом всё подряд. Фильтр стал бы агрессивнее, а не точнее, то
   есть фича сделала бы ХУЖЕ, чем было. Берётся не более N каждой метки, и
   берутся свежие: спам меняется, прошлогодние схемы учат вчерашней войне.
2. **Защита лог-канала от потока.** Спамер с пятьюдесятью одинаковыми
   сообщениями иначе превратил бы канал в ленту из пятидесяти одинаковых
   запросов, и владелец перестал бы читать её целиком, вместе с полезными.
   Неразмеченный вердикт с тем же нормализованным текстом второй раз не
   заводится. Именно НЕРАЗМЕЧЕННЫЙ: если решение уже вынесено, а текст
   пришёл снова, это новый случай — решение могло измениться.

Плюс потолок на длину блока примеров: промпт оплачивается на КАЖДОМ вызове,
и без потолка стоимость модерации тихо росла бы вместе с числом размеченных
примеров — фича дорожала бы тем сильнее, чем активнее ей пользуются.

**Права.** Размечать может только администратор ИСХОДНОГО чата — того, чью

Тесты: 20 в `tests/test_spam_learning.py`, включая перехват реального

снятии падают ровно два теста.

### Исходная постановка F57 (для истории)  ⭐ ГЛАВНЫЙ РЫЧАГ
Подсмотрено у tg-spam (umputun): спорные вердикты уходят в очередь с
кнопками «спам / не спам», и каждое решение модератора делает классификатор
точнее именно на этой аудитории.

выборку и подмешивать few-shot примерами в промпт. Без переобучения модели:
few-shot из своих же примеров даёт основной эффект за долю усилий.

### F58 — Purge и репорты от участников (РЕАЛИЗОВАНО 2026-08-15)

**ОГРАНИЧЕНИЯ TELEGRAM ОПРЕДЕЛИЛИ ДИЗАЙН, а не наоборот:**

- Bot API **не умеет перечислять сообщения чата**. Значит `/purge` работает
  по ДИАПАЗОНУ id — от того, на что ответили, до самой команды. Часть id в
  диапазоне не существует; ошибки по отдельным сообщениям глотаются, потому
  что «дырки» здесь норма, а не сбой;
- бот **не удаляет сообщения старше 48 часов**. «Зачистить всё за неделю»
  невозможно в принципе, и подсказка об этом прямо говорит: иначе владелец
  решит, что не сработало из-за поломки;
- диапазон ограничен `MAX_PURGE`: ответ на старое сообщение иначе
  превратился бы в тысячи бесполезных запросов к API.

**Репорт: команда удаляется всегда** — она не должна висеть в чате и тем
более привлекать внимание к сообщению, на которое жалуются. Пауза между
жалобами от одного человека обязательна: недовольный участник иначе забьёт
лог-канал жалобами на оппонента, и модератор перестанет читать канал целиком.

**Решение по жалобе принимает админ ИСХОДНОГО чата**, а не лог-канала:
доступ к каналу логов сам по себе не делает человека модератором группы.

Тесты: 14.

### Исходная постановка F58 (для истории)
Purge подсмотрен у Rose, репорты — у Combot.

- **Purge** — удаление диапазона сообщений одной командой. Сейчас чат после
  рейда чистится руками, при том что детектор рейда у нас есть.
- **`/report`** — участник жалуется кнопкой, жалоба уходит модераторам.
  Человек видит спам раньше фильтра, но сейчас не может сообщить об этом,
  не имея прав. Ложится на существующий лог-канал с inline-кнопками
  (`guardian/services/log_channel.py`) — новой инфраструктуры не нужно.

Греп `purge` и `report` по `*.py`: 0 вхождений.

### F59 — UTM-метки на исходящих ссылках (РЕАЛИЗОВАНО 2026-08-15)

**Главный риск — испортить текст поста.** Пост уходит подписчикам ОДИН РАЗ,
и битая ссылка в нём — это не «поправим и перевыложим», а потерянные
переходы и вопрос «что у вас с ссылками». Отсюда консервативный разбор:

- **ссылки на Telegram не размечаются вообще** (`t.me`, `telegram.me`,
  `telegra.ph`): метки там бессмысленны, а инвайт-ссылку лишний параметр
  может сломать. Проверка по границе домена — `nott.me` это не `t.me`;
- **хвостовая пунктуация остаётся в тексте**: «Подробнее: example.com/post.»
  — точка тут конец предложения, и втянув её в ссылку, мы получим 404 у
  каждого, кто перейдёт;
- **уже размеченная ссылка не трогается** — иначе повтор поста (F55) удвоил
  бы метки;
- существующие параметры и якорь сохраняются.

**Метки проставляются в момент публикации, а не при рерайте.** Так в превью
модерации видно ровно то, что уйдёт, а смена настроек не требует
переписывать готовые посты.

В шаблон кампании подставляется `{post_id}`, а не дата: id однозначно
указывает на пост, а «2026-08-15» смешает все посты одного дня.

Тесты: 20.

### Исходная постановка F59 (для истории)
Подсмотрено у SMMplanner и NovaPress. Дописывать `utm_source/medium/campaign`
к внешним ссылкам при публикации, шаблон настраивается, привязка к посту
сохраняется. Греп `utm_source`: 0 вхождений.

**Не дубль связки «вариант → просмотры»** (F53/post_variants): та про
происходящее ВНУТРИ Telegram, эта — про то, что снаружи. Если канал гонит
трафик на сайт, сейчас невозможно понять, какой пост принёс переходы.

### F60 — Детектор накрутки по кривой роста (РЕАЛИЗОВАНО 2026-08-15, ПОДКЛЮЧЁН К UI 2026-08-16)

> ⚠️ **Урок, который стоит запомнить.** Фича была помечена реализованной,
> имела собственные тесты и была написана правильно — но `analyze()` не
> вызывался НИОТКУДА: ни роут, ни джоба, ни шаблон. То есть владелец не имел
> никакого способа увидеть её вывод, а тесты этого не показывали, потому что
> проверяли модуль напрямую.
>
> Найдено сквозным аудитом 2026-08-16 поиском вызовов, а не чтением кода.
> Теперь отчёт выводится на `/stats/growth` — там же, где живут те самые
> снимки, по которым он и считается, — и это закреплено тестами именно на
> СВЯЗЬ детектора со страницей.
>
> **Правило на будущее:** «реализовано» означает, что до фичи можно дойти
> из интерфейса. Модуль с тестами, но без единого вызова — это не фича.

**Почему это можем мы, а разовые чекеры — нет.** У бота, которому скормили
ссылку на канал, есть один снимок. Накрутка видна не в точке, а в ФОРМЕ
кривой, а форма нужна за недели. У нас история собирается с первого дня
(F22), у чекера её нет и взять неоткуда.

**ДВА СИГНАЛА, А НЕ ТРИ.** В методиках называют три: «пила», рост без
охватов и ступеньки в нерабочее время. Третий НЕ считаем: снимки делаются
раз в несколько часов, разрешения по часам у нас нет. Посчитать «примерно»
значило бы выдать шум за улику — а на этих цифрах человек решает, платить
ли за размещение.

**Формулировки осторожные намеренно:** «есть признаки», а не «накрутка».
Детектор видит форму кривой, а не намерение.

Половина тестов — про ЛОЖНЫЕ СРАБАТЫВАНИЯ. Виральная публикация тоже даёт
резкий приход; разница в том, что эти люди остаются, и обвинять владельца в
накрутке за удачный пост недопустимо. Детектор, кричащий на любой всплеск,
приучает не смотреть на предупреждения — и настоящую накрутку пропустят.

Тесты: 16. Проверено на осмысленность: при снятии условия оттока падают
четыре теста против ложных срабатываний.

### F61 — Force-subscribe: обязательная подписка на канал (РЕАЛИЗОВАНО 2026-08-15)

Прямая воронка «участник группы → подписчик канала». Механика — один вызов
`getChatMember`, платить за неё сторонним ботам не за что.

**ЭТО БАРЬЕР НА ВХОДЕ В ОБЩЕНИЕ**, и почти вся работа ушла в то, чтобы он не
стал отталкивающим:

- **проверка fail-open.** Если Bot API не ответил или бот не админ в канале,
  сообщение ПРОПУСКАЕТСЯ. Перекрыть чат из-за сетевой ошибки хуже, чем
  пропустить одного неподписанного — тот же принцип, что у AI-фильтра.
  `is_subscribed` возвращает `None`, а не `False`: «не знаем» и «не
  подписан» разные вещи, и схлопнув их, мы начали бы удалять сообщения при
  каждом сбое сети;
- **человеку говорят, что произошло, и дают ссылку.** Молча удалённое
  сообщение выглядит как поломка чата, а не как правило: новичок решит, что
  его забанили ни за что, и уйдёт — вместо того чтобы подписаться, ради чего
  всё и затевалось;
- **напоминание не чаще раза в N минут**, иначе пять сообщений подряд дадут
  пять уведомлений. При этом пауза касается ТОЛЬКО напоминания: удаление
  продолжает работать, иначе правило отключалось бы на пять минут после
  первого срабатывания;
- **администраторы освобождены** — владелец, забывший подписаться на
  собственный канал, не должен упереться в свой же запрет.

Проверяется ПОСЛЕ доверенных (требовать подписку с доверенного значит
наказывать за лояльность) и ДО фильтров (тратить AI-вызов на сообщение,
которое всё равно удалят, незачем).

Тесты: 17. Fail-open проверен на осмысленность: при его снятии падает ровно
тот тест, который его защищает.

### Исходная постановка F61 (для истории)
Подсмотрено у GroupHelp: участник не может писать в группе, пока не подписан
на связанный канал. Прямая воронка «участник группы → подписчик канала».

Механика — один вызов `getChatMember`, платить за неё сторонним ботам не за
что. Настройка на группу, обязательно с белым списком и понятным сообщением
(иначе новичок просто не поймёт, почему его сообщения не проходят).
Греп `force_subscribe|require_subscription`: 0 вхождений.

### F62 — Маркировка рекламы: ОРД и erid (РЕАЛИЗОВАНО 2026-08-16, ВЫКЛЮЧЕНО ПО УМОЛЧАНИЮ)

**Как устроено.** Настройка `ad_marking_enabled`, по умолчанию выключена.
Реквизиты и токен живут на БРИФЕ (`ad_briefs.advertiser_legal_name`,
`advertiser_inn`, `erid`), потому что ОРД выдаёт токен на креатив, а креатив
здесь — это бриф: из него рождается ровно один пост. Заявка рекламодателя
(F66) несёт те же поля и КОПИРУЕТ их на бриф при принятии — заявку могут
поправить позже, а в отчёт должно уйти то, что стояло в самом посте.

**ПОМЕТКА ИДЁТ В НАЧАЛО ПОСТА.** Telegram сворачивает длинный текст под
«показать полностью»; пометка в конце формально есть, а фактически не
видна — то есть не делает единственное, ради чего существует.

**ПОСТ БЕЗ erid НЕ ПУБЛИКУЕТСЯ ВОВСЕ**, когда маркировка включена. Не
«публикуется без пометки», не «публикуется с предупреждением» — отказ с
причиной в `status_reason`. Опубликовать с половиной маркировки хуже, чем не
опубликовать: ушедший пост не отозвать, а штраф выписывают за факт
размещения.

**Отчёт показывает и НЕмаркированные размещения** — именно они и создают
проблему, прятать их в красивом отчёте бессмысленно.

**Пометка видна при модерации**, хотя приписывается при публикации: владелец
подтверждает пост, а пометка — юридическое заявление о том, кто
рекламодатель. Увидеть её впервые уже в канале значило бы согласовать
вслепую.

**Интеграции с API ОРД НЕТ и не планируется на этом этапе.** Регистрация
креатива требует договора с оператором и делается вне системы; владелец
получает токен там и вставляет в бриф. Изображать автоматизацию, которой не
происходит, — худший вариант из возможных для фичи про соответствие закону.

Миграция `0042_ad_marking`. Тестов 24 (17 логики + 7 интерфейса).

**Перед включением сверить** суммы штрафов и порядок отчётности по
действующей редакции — в этом файле их нет намеренно.

> **Решение владельца:** сделать механику и держать под выключателем до
> первого реального рекламодателя.
>
> **Поправка к постановке ниже.** Записано было «маркировка противоречит
> нативности» — по сути противоречия нет: обязанность маркировать привязана
> к рекламе как таковой, а не к её формату. Нативный пост не перестаёт быть
> рекламой оттого, что не выглядит ею. Реальный выбор был не «нативно или с
> пометкой», а «продаём ли рекламу российским рекламодателям» — и ответ

>
> **Суммы штрафов и порядок отчётности НЕ проверены** и в этом файле не

Не заимствование у конкурента, а требование закона РФ. Реклама должна нести
erid-токен от оператора рекламных данных, пометку «Реклама» с указанием
рекламодателя, и попадать в отчётность ОРД до 30-го числа следующего месяца.

**Единственный пункт всего бэклога, где цена бездействия — штраф, а не

и ноль маркировки (греп `erid|ОРД|маркировк`: 0 вхождений).

**Почему это не задача разработчику, а решение владельца.** Маркировка по
смыслу противоречит F21: нативная реклама работает ровно потому, что не
выглядит рекламой, а обязательная пометка её обнажает. Технически задача
несложная — поле `erid` на пост, пометка в шаблоне, выгрузка отчёта. Но
сначала нужно решить, что делать с нативностью, а уже потом писать код.

Штрафы по ст. 14.3 КоАП для юрлиц измеряются сотнями тысяч рублей;
законодательство менялось несколько раз — суммы и порядок сверить перед
запуском, не полагаться на цифры из этого файла.

### Общая точка для метрик поста (СДЕЛАНО 2026-08-15)
Не фича, а вычищенный технический долг — записан, чтобы следующая сессия не
завела пятую копию.

Запрос «взять последний снимок из `post_stats`» был написан ЗАНОВО в четырёх
местах: `scheduler/stats.py` (F14), `scheduler/digest.py` (F20),
`engagement_repo.py` (F53) и `scheduler/recycle.py` (F55). Все четыре
писались независимо, и все четыре повторили одну ошибку — сортировку только
по `captured_at`, без тай-брейка по `id`. Часы на Windows тикают ~15 мс,
поэтому два замера подряд регулярно получают одинаковую метку, а при
равенстве порядок строк не определён. В `scheduler/stats.py` ошибка жила с
момента написания F14: цифры в `/stats` могли браться из устаревшего замера.

Это тот же сценарий, что привёл к F51 (правила приёма скопировали в две
ветки, копии разошлись), и лечение то же — общая точка вместо копий:
`tg_repost/post_stats_repo.py`.

Побочно ушёл **N+1**: три из четырёх мест ходили в базу в цикле по постам,
теперь один запрос на весь список. Тест это фиксирует, считая реально
выполненные SELECT-ы.

**Правило на будущее:** просмотры поста берутся ТОЛЬКО через
`post_stats_repo`. Свой `ORDER BY captured_at` — это пятая копия и пятое
повторение той же ошибки.

## P6 — бизнес-обвязка: продукт «всё в одном» (F63–F74)

> **Зачем этот раздел.** По контенту мы сильнее рынка: двухагентная редакция
> (F40) и сюжеты (F51) не встречаются НИ У ОДНОГО из 53 разобранных
> продуктов. По бизнес-обвязке — пусто: ни денег, ни CRM, ни поддержки, ни
> команды. То есть у системы отличный редакционный конвейер, но нет ничего,
> что превращает аудиторию в выручку.
>
> ⚠️ **РАЗВИЛКА, БЕЗ КОТОРОЙ НЕЛЬЗЯ ПРОЕКТИРОВАТЬ СХЕМУ БД.**
> «Для бизнеса» читается двумя способами, и они ведут к разной архитектуре:

записано там как осознанный выбор. Сбой Guardian НЕ роняет карточку: это
отдельная БД и отдельный процесс, и его молчание не повод не показать
владельцу всё остальное. Проверено тестом.

**Мелочи, которые дороже, чем кажутся:**
- теги нормализуются («VIP», «vip», «vip » — один тег). Иначе сегмент по
  одному написанию молча теряет две трети людей, и заметно это станет
  только по недоставленной рассылке;
- тег вешается на ЧЕЛОВЕКА, без `chat_id`: «постоянный покупатель» остаётся
  таковым во всех группах, иначе одного и того же человека пришлось бы
  размечать заново в каждом чате;
- очки суммируются по всем чатам, серия берётся лучшая — для владельца это
  один человек, а не несколько независимых участников;
- в карточке считаются только ПОДТВЕРЖДЁННЫЕ рефералы: неподтверждённый ещё
  не доказал, что он живой человек (F42).

**СЕГМЕНТ — ЭТО ЗАПРОС, А НЕ СПИСОК.** Материализованный список устаревает
молча: человек ушёл из чата или перестал подходить под условие, а рассылка
всё равно уходит ему — и узнаётся это по жалобам. Хранится только фильтр,
состав вычисляется в момент обращения.

**Главная опасность сегментов — выборка «вся база» по ошибке.** Опечатка в
имени условия, пустой фильтр, потерянное поле — и рассылка (F64) уходит всем
подряд. Отменить невозможно: сообщения доставлены. Ключевая мысль: молча
проигнорированное условие НЕ СУЖАЕТ выборку, то есть опечатка `tagg` вместо
`tag` превращает «только VIP» во «всех». Поэтому:

- неизвестные условия отвергаются, а не игнорируются;
- пустой фильтр отвергается;
- «все» — отдельное явное условие `everyone`, не сочетающееся с другими;
- проверка вызывается и в `evaluate`, а не только при сохранении, и идёт
  ПЕРЕД записью: битый сегмент не должен попасть в базу даже на секунду;
- в UI размер сегмента считается при каждом показе — цифра «1» против
  «8420» единственное, что отличает узкую выборку от всей базы.

Условия комбинируются через И. Если бы складывались, сегмент «VIP и с 500
очками» оказался бы шире каждого из них по отдельности.

**Что осталось на потом:** покупки в карточке — появятся вместе с F49.

### F64 — Рассылки по сегменту (РЕАЛИЗОВАНО 2026-08-15, ВОЗВРАТ ДОБАВЛЕН 2026-08-16)

> **Отписавшийся не мог вернуться.** Функция `resubscribe` была написана и

>

> это отсутствие возможности. Отдельная команда, а не кнопка: кнопка живёт в
> рассылке, а отписавшемуся рассылки больше не приходят — нажимать негде.

Здесь сошлись три построенные раньше вещи: сегмент даёт список людей (F63),
реестр подписчиков отвечает, кому из них МОЖНО написать, очередь задач
делает отправку возобновляемой после обрыва (фаза 11).

**ГЛАВНОЕ ОГРАНИЧЕНИЕ — НЕ НАШЕ.** Telegram не даёт боту написать первым:
личная переписка открывается только когда человек сам нажал «Запустить» или
пришёл по deep-link. Поэтому сегмент из 8000 участников группы может быть
достижим на сотню человек. Введён реестр подписчиков (`bot_subscribers`,
миграция `0035`), который пишется на `/start` бота Engage.

**Три причины недостижимости — разные состояния с разными правилами:**
не запускал бота (обычное дело, не ошибка), заблокировал (решение Telegram,
снимается только его же сообщением), отписался кнопкой (его решение,
сообщение боту его НЕ отменяет — иначе любой вопрос возвращал бы человека в
рассылку, от которой он отказался).

**Четыре правила, без которых рассылка опасна:**
1. кнопка отписки в КАЖДОМ сообщении — без неё единственный способ
   прекратить поток — заблокировать бота, а это потеря человека целиком;
2. блокировка — не ошибка: отдельный счётчик, повторов нет;
3. курсор по возрастанию `user_id` — после обрыва рассылка продолжается;
4. пауза между отправками — превышение частоты стоит не задержки, а
   временного запрета на отправку целиком.

**Интерфейс двухшаговый**, и это не про удобство: разосланное не отзывается.
Между «написал текст» и «ушло» стоит экран с двумя цифрами и разбивкой по
причинам. Подтверждение несёт снимок показанных чисел: если состав сегмента
изменился между экранами, владельца возвращают на предпросмотр вместо тихой
отправки по другому списку.

**Таблица рассылок отдельно от очереди** (`broadcasts`, миграция `0036`):
задача — механика и живёт до завершения, рассылка — документ, нужный и через
месяц. Имя сегмента сохраняется на момент отправки.

**Побочно:** обработчики очереди переведены на асинхронные — синхронная
сигнатура заставила бы звать `asyncio.run` внутри работающего цикла событий,
то есть не работала бы вовсе. Ошибка формы вскрылась на первом же реальном
потребителе.

Тесты: 17 (реестр) + 16 (рассылка) + 14 роутовых. Три защиты проверены на
осмысленность: при игнорировании курсора падают 6 тестов, при смешивании
блокировки с отпиской — 1, при отключении сверки чисел — 1.

### F65 — Медиакит и отчёт рекламодателю (РЕАЛИЗОВАНО 2026-08-15)

Самая дешёвая фича блока: **ни одного нового сбора данных**. ERR и средние
охваты считает F53, динамику подписчиков собирает F22, метрики постов —
F14/F31, долю включённых уведомлений — F56. Здесь только сборка в документ.

**ЧЕСТНОСТЬ ВАЖНЕЕ КРАСИВОЙ ЦИФРЫ** — медиакит документ для переговоров, и
заинтересованная сторона в нём мы:

- показывается **покрытие данными**: средний охват по одному замеренному
  посту из сорока — это не средний охват, и оговорка обязательна;
- **один замер подписчиков не даёт прироста.** Разница значения с самим
  собой — не «нулевой рост», а «мы не знаем»; показать «+0» значило бы
  соврать;
- **пост без замеров не может попасть в «лучшие»** — мы про него ничего не
  знаем, и место в витрине он занял бы незаслуженно;
- отсутствующие данные показываются как отсутствующие, а не как ноль;
- при полном отсутствии охватов документ прямо говорит «данных мало» —
  лучше, чем отдать пустоту и получить вопрос без ответа.

**ПУБЛИЧНОЙ ССЫЛКИ НЕТ НАМЕРЕННО.** Отдавать медиакит по токену без входа
удобнее, но это добавило бы публичный маршрут, а вся защита системы построена
на обратном: в `webui/auth.py` записано, что CSRF-токенов нет, потому что
«нет сторонних origin». Один публичный роут ломает эту предпосылку.
Рекламодателю уходит PDF — страница печатается браузером, разметка под
печать готова. Если публичная ссылка понадобится, её место в F73, где модель
угроз пересматривается целиком.

Тесты: 17. Честность прироста проверена на осмысленность: если считать
дельту по одному замеру, падает ровно тот тест, который это запрещает.

### F66 — Приём заявок рекламодателей (РЕАЛИЗОВАНО 2026-08-15)

**Недостающее звено между F21 и F35.** Бриф — это уже принятая к работе
задача для ИИ, журнал дохода — уже полученные деньги, а как заявка приходит
и чем занято расписание, не знал никто: владелец держал это в переписке.
Теперь цикл `new → accepted → published` (либо `declined`) живёт в системе,
принятие СОЗДАЁТ бриф, публикация — запись дохода. Вопрос «сколько мы
заработали на этом рекламодателе» перестаёт быть вопросом к памяти.

**ДВОЙНАЯ ПРОДАЖА МЕСТА — то, ради чего здесь есть логика, а не CRUD.** Две
принятые заявки на одну дату означают, что владелец пообещал одно и то же
двоим, и узнает об этом кто-то из них уже после оплаты. Извинением такое не
исправляется. Проверка живёт в `accept`, а не в ограничении базы: человеку
надо СКАЗАТЬ, с кем конфликт, а не показать ошибку уникальности — поэтому
исключение несёт саму конфликтующую заявку.

**Решения помельче, но важные:**
- заявка — это ПРОСЬБА, а не бронь: конфликт при создании не проверяется.
  Пусть придут трое на одну дату, выберет владелец; отвергать входящие за
  него значит терять деньги на ровном месте;
- **отклонённая заявка место не держит** — иначе один отказ блокировал бы
  день навсегда;
- бриф создаётся с `max_uses=1`: заявка оплачена за ОДНО размещение, а
  бриф без лимита ИИ взял бы повторно — бесплатная реклама за наш счёт;
- сумму при публикации можно переопределить: договорились на одну цену,
  получили другую, и врать журналу незачем;
- опубликованную заявку нельзя удалить — за ней стоит запись дохода.

**Календарь и список — на ОДНОЙ странице.** Решение «принять или отказать»
нельзя принять, не видя, что уже стоит на эту дату: разнеси их по вкладкам —
и владелец начнёт принимать вслепую, а потом извиняться. Конфликт
показывается текстом С ИМЕНЕМ конкурента, а не «дата занята»: сообщение без
имени превращает решение в угадывание.

Миграция `0037_ad_requests`. Тесты: 20 + 15 роутовых. Защита от двойной
продажи проверена на осмысленность: при снятии проверки падают ровно два
теста.

### F67 — Affiliate: деньги поверх реферальной программы (РЕАЛИЗОВАНО 2026-08-16)
Подсмотрено у InviteMember, где партнёрский движок — ключевая фича.

**F42 уже сделал сложную часть** — антифрод: реферал подтверждается только
если приглашённый вступил, написал и прожил N дней.

**ТРИ МЕСТА, ГДЕ ПАРТНЁРСКАЯ ПРОГРАММА ТЕЧЁТ, и каждое закрыто тестом:**

1. **Возврат платежа.** Человек платит 100, партнёр получает 30, человек
   возвращает деньги — и у владельца минус 30 из воздуха. Возврат ОБЯЗАН
   отменять начисление, и отмена делается отрицательной строкой в журнале,
   а не удалением: удалённая история не объясняет партнёру, куда делись его
   деньги.
2. **Самоприглашение.** Второй аккаунт, приглашённый самим собой,
   превращает комиссию в скидку. На себя не начисляется никогда, даже если
   реферал прошёл все проверки F42.
3. **Повтор.** Тот же платёж может обработаться дважды — ключ
   идемпотентности стоит в базе, а не только в коде.

**Баланс — это сумма строк, а не поле.** Поле пришлось бы менять при каждой
оплате, возврате и выплате; потерянная правка разошлась бы с историей
навсегда, а сумму пересчитать можно всегда.

**Процент хранится НА НАЧИСЛЕНИИ.** Настройку поменяют, а прошлые
начисления должны остаться объяснимыми.

**ВЫПЛАТЫ — ВРУЧНУЮ, И ЭТО НЕ НЕДОДЕЛКА.** Telegram не даёт боту переслать
звёзды человеку: вывод идёт через Fragment на кошелёк владельца, дальше он
платит партнёру как договорились. Кнопка называется «записать выплату» и
ровно это и делает; кнопка, изображающая перевод, была бы обманом. Запись
выплаты больше долга отклоняется — неправда в истории не распутывается.

Миграция `0044_affiliate`. Страница `/affiliate` — только владелец. По
умолчанию процент 0, то есть программа выключена: комиссия по умолчанию
означала бы раздачу доли выручки без решения владельца. Тестов 32.

### F68 — Поддержка: единый инбокс обращений (РЕАЛИЗОВАНО 2026-08-15)

Вопрос, написанный боту в личку, до сих пор не превращался ни во что. Для
бизнеса блок обязательный: человек, которому не ответили, не пишет второй
раз — он уходит.

**ОДИН ТРЕД НА ЧЕЛОВЕКА, а не на обращение.** Человек не мыслит «тикетами»:
пишет, дописывает, возвращается через неделю. Нарезка по таймауту породила
бы три треда об одном и том же и заставила оператора собирать историю по
кускам. Закрытый тред открывается заново новым сообщением — это и есть
«вернулся с тем же вопросом», и оставить его закрытым значило бы потерять
обращение.

**Карточка человека (F63) — рядом с перепиской.** Отвечать незнакомцу и
отвечать тому, кто привёл десять друзей, — разные разговоры, и оператор
должен видеть разницу не переключая страницы.

**Ответ уходит ТЕМ ЖЕ ботом**, которому человек написал: ответ от другого
бота для него сообщение от неизвестного адресата, и половина решит, что это
спам. Сбой отправки НЕ теряет текст — оператор потратил на него время, и
предупреждение с возможностью отправить снова лучше, чем пустое поле.

**Перехватчик в Engage регистрируется СТРОГО ПОСЛЕДНИМ.** Он ловит любое
личное сообщение, не разобранное выше; поставь его раньше — и он проглотит
текст, который ждёт предложка (F47 держит его через FSM-состояние), а
обнаружится это по тишине в ответ на обычные команды.

Только личка: сообщения в группе — работа модерации, а не поддержки.
Подтверждение приёма обязательно, иначе человек не знает, дошло ли, пишет
второй раз и уходит.

Миграция `0040_support`. Тесты: 20 + 12 роутовых.

### Исходная постановка F68 (для истории)
Подсмотрено у Chatwoot. Обращения из лички бота и из группы — в один
список: назначение оператору, статусы, история переписки с человеком,
время реакции.

Для бизнеса блок обязательный: вопрос в личку боту сейчас не превращается
ни во что. Частично ложится на существующий лог-канал с inline-кнопками, но
нужен веб-интерфейс — в Telegram-канале список обращений не ведут.

Связано с F63: обращение должно цепляться к карточке человека, иначе
оператор каждый раз общается с незнакомцем.

### F69 — Магазин в боте (РЕАЛИЗОВАНО 2026-08-16, вместе с F70)
Подсмотрено у AiogramShopBot и примеров Bot Payments API. Прямые продажи из
канала без внешнего сайта.

**СДЕЛАН ВМЕСТЕ С F70, И ЭТО НЕ УКРУПНЕНИЕ ЗАДАЧИ.** F70 сам по себе —
платёжный слой, до которого нельзя дойти из интерфейса, то есть ровно тот
мёртвый код, из-за которого F60 числилась готовой и не работала. Правило
записано там же: «реализовано» означает, что до фичи можно дойти.

**КОРЗИНЫ НЕТ ОСОЗНАННО.** Один товар — один счёт. Корзина это состояние
между сообщениями, а состояние в боте живёт до перезапуска процесса; за
корзиной идут «изменить количество», «удалить позицию», «промокод» — и
получается интернет-магазин внутри мессенджера. Добавим, когда появится
реальная потребность в двух товарах в одном заказе.

**ЦЕНА ЦЕЛЫМ ЧИСЛОМ В КОПЕЙКАХ.** Так требует Bot Payments API, и так же не
возникает классической ошибки денег: дробные рубли дают
0.1 + 0.2 = 0.30000000000000004, а расхождение с эквайрингом ищут неделями.
Владелец вводит рубли — перевод в одном месте, а не в каждой форме.

**ОСТАТОК СПИСЫВАЕТСЯ ПРИ ОПЛАТЕ, А НЕ ПРИ ОТКРЫТИИ СЧЁТА.** Иначе брошенные
корзины съедают склад. Цена выбора — двое могут оплатить последний товар
одновременно; отказать ПОСЛЕ оплаты нельзя, поэтому второй заказ
принимается и помечается `is_oversold`. Владелец увидит и решит, вернуть
деньги или довезти. Молча потерять один из двух заказов было бы хуже:
покупатель узнал бы об этом сам, когда посылка не пришла.

**ПРОВЕРКА ОСТАТКА ЖИВЁТ В `pre_checkout`** — единственный момент, когда
Telegram спрашивает нас до списания денег. Отказ там человек переживёт.

**ДВА ВИДА СЧЕТОВ В ОДНОМ БОТЕ.** Подписка идёт за Stars без провайдера,
товары — за рубли через провайдера. Обработчик оплаты у Telegram один,
поэтому счета различаются префиксом payload (`sub:` и `ord:`). Без фильтра
`pre_checkout` подписки отвечал бы и на товары, отклоняя их как «чужой
канал», — покупка в магазине была бы невозможна вовсе.

**Адрес доставки запрашивает Telegram** (`need_shipping_address`), а не мы
своим диалогом: свой означал бы четыре сообщения вместо одной формы.

Миграция `0045_shop`. Страница `/shop` — только владелец: цена это деньги, а
в заказах адреса и телефоны покупателей. Тестов 60.

**Аудит 2026-08-16 нашёл в этой фиче три дыры, все закрыты:**

1. **Дубль заказа держался только проверкой в коде.** В платёжном журнале
   F49 такое же правило с самого начала стоит ограничением в базе, а здесь
   его не было: между проверкой «заказа ещё нет» и вставкой помещается
   вторая доставка апдейта, и покупатель получает две посылки за одни
   деньги. Миграция `0046_order_charge_unique`.
2. **Удаление товара оставляло в заказах ссылку в никуда.** На SQLite это
   проходило молча (`PRAGMA foreign_keys` = 0), на Postgres тот же вызов
   упал бы нарушением внешнего ключа — ошибка ждала переезда. Теперь товар
   с заказами не удаляется, а снимается с продажи.
3. **Отменённый заказ можно было оживить.** За отменой обычно стоит возврат
   денег, и воскресший заказ означал бы обещание товара за возвращённые
   деньги. Отправленный и отменённый — терминальные состояния.

### F70 — Платежи рублями и криптой (РЕАЛИЗОВАНО 2026-08-16, НЕ ПРОВЕРЕНО ЖИВЫМИ ДЕНЬГАМИ)

**Три способа приёма крипты, каждый настраивается отдельно и назначается
группе.** Требование владельца: групп много, условия и кошельки разные.
Поэтому способы — таблица, а не настройка: настройка означала бы один
кошелёк на всю систему.

**Различаются они не API, а курсом** — это главное:

| Способ | Комиссия | Кто считает курс |
|---|---|---|
| CryptoBot (Crypto Pay) | провайдера | он сам, сумму называем в фиате |
| Wallet Pay | провайдера | он сам, сумму называем в фиате |
| Прямо на TON-кошелёк | нет вовсе | никто — товар оценивается в TON |

**Курс со сторонних сервисов не берём принципиально.** Сервис соврёт или
ляжет — владелец недополучает на каждой продаже и замечает через месяц по
не сходящейся выручке. Прямой перевод честно отказывается принимать
рублёвую цену вместо того, чтобы придумать пересчёт.

**Опрос вместо вебхуков** у всех трёх: система не обязана торчать наружу
ради приёма денег. Задача переопрашивает себя через очередь фазы 11, поэтому
переживает рестарт. Предел — числом попыток, а не «счёт протух»: у прямого
перевода истекать нечему, деньги могут прийти и через сутки.

**Прямой перевод опознаётся по комментарию** — единственной связи платежа с
заказом: на кошелёк иначе приходят неотличимые суммы. Недоплата оплатой не
считается.

**Ключи шифруются** мастер-ключом админки и наружу не отдаются никогда: в
объекте для шаблона поля с ключом просто НЕТ. Адрес TON-кошелька, наоборот,
показан открыто — по нему владелец сверяется с кошельком.

**Кошелёк запоминается В ЗАКАЗЕ.** Владелец может переназначить кошелёк
группы, пока счёт висит неоплаченным, — проверять надо старый: деньги придут
туда, куда человеку показали ссылку.

**Остаток списывается при подтверждении, а не при выставлении счёта.** Иначе
брошенные корзины занимали бы склад. Товар, закончившийся за время ожидания,
не отменяет оплаченный заказ — он помечается как проданный сверх остатка.

**Заказ создаётся ПОСЛЕ успешного счёта.** Заказ без счёта — строка, которую
никто не оплатит; она висела бы в неоплаченных, изображая потерянную продажу.

⚠️ **НИ ОДИН СПОСОБ НЕ ПРОВЕРЕН НА ЖИВЫХ ДЕНЬГАХ.** Формы запросов взяты из
документации, а не подтверждены опытом. Перед боевым включением каждый
прогнать на копеечной сумме.

Тесты: 54 (27 на способы, 13 на страницу, 14 на оплату из бота).

#### Исходная постановка

> **Сделан вместе с F69** — платёжный слой без магазина был бы кодом, до
> которого нельзя дойти. Токен провайдера — секрет `shop_provider_token`,
> читает его Engage: счета за товары выставляет он.
>
> **Крипта НЕ реализована, и причина конкретная.** Crypto Pay API и Wallet
> Pay сообщают об оплате ВЕБХУКОМ, то есть требуют публично доступного
> эндпоинта. Сейчас у админки его нет вовсе — она целиком за логином, и это
> записанный трейдофф модели угроз (см. F73, где он же и блокирует
> публичный API). Городить публичный вебхук ради крипты значит пересмотреть
> модель угроз, а не дописать адаптер.
>
> **Обходной путь, если крипта понадобится:** опрос статуса счетов вместо
> вебхука. Crypto Pay API умеет отдавать список инвойсов по запросу — тогда
> публичный эндпоинт не нужен, а задержка в минуту для оплаты товара
> некритична. Это дешевле пересмотра модели угроз и делается поверх
> готового журнала операций.

Подсмотрено у Prodamus, CryptoBot (Crypto Pay API), OxaPay.

**Дополняет F49, а не заменяет.** Разделение жёсткое и задано правилами
Telegram: цифровые товары в ботах и мини-аппах — ТОЛЬКО Stars (иначе бан),
физические товары и услуги — обычный эквайринг через Bot Payments API с
провайдером.

Провайдер подключается в @BotFather. Список провайдеров менялся, часть
российских отключалась из-за санкций — актуальность сверять на момент
подключения, а не по этому файлу.

**Крипта (TON, USDT) живёт ЗДЕСЬ, а не в подписке.** Вопрос разбирался
2026-08-16 по запросу владельца: принимать TON/USDT за доступ в канал
нельзя — это цифровой товар, и обход Stars ведёт к бану бота. За физические
товары магазина крипта допустима, и тогда пригодятся Crypto Pay API,
Wallet Pay или прямой перевод с проверкой в блокчейне. Подробный разбор — в
F49.

### F71 — Воронки: движок сценариев (РЕАЛИЗОВАНО 2026-08-15)

Зачатки были: F45 (триггеры) и F46 (онбординг) — воронка без движка. Теперь
цепочки собираются без правки кода, а отложенные шаги едут на очереди задач
из фазы 11.

**ЛИНЕЙНЫЕ ЦЕПОЧКИ, БЕЗ ВЕТВЛЕНИЙ — осознанный предел.** Полноценный движок
сценариев разрастается бесконечно: за ветвлением просят циклы, за циклами
переменные, и получается плохой язык программирования внутри админки.
Реальные задачи владельца — онбординг и цепочка напоминаний — линейны. Если
ветвление понадобится, добавить его к линейному движку легче, чем убрать
лишнее из универсального. Drag-n-drop конструктора нет по той же причине,
что записана в исходной постановке.

**ЧЕТЫРЕ ПРИЧИНЫ ОСТАНОВКИ, каждая обязательна:**
- **человек отписался** — от рассылок он отказался, а воронка тоже рассылка;
  продолжать значит игнорировать прямой отказ;
- **стал недостижим** (заблокировал бота) — писать некуда;
- **воронку выключили** — владелец передумал, и цепочка не должна доигрывать
  сама по себе неделю после этого;
- **шаги изменились** и следующего больше нет — честно завершаем, а не
  продолжаем с чужого места.

Причина остановки записывается: без неё «остановлена» выглядит как сбой.

**Повторная запись невозможна** — человек, дважды нажавший «Запустить»,
иначе получил бы всю цепочку дважды. Защита двойная: проверка в коде даёт
внятный ответ, уникальное ограничение в БД ловит гонку (проверено — при
снятии кодовой проверки падает ограничение).

**Следующий шаг — ОТДЕЛЬНАЯ задача с своим `run_after`**, а не курсор внутри
текущей: курсор годится для порции работы подряд, а между шагами сутки —
держать ради этого задачу в очереди значило бы занять воркер на день.

**ИНТЕРФЕЙС — ФОРМА, А НЕ КОНСТРУКТОР** (`/funnels`). Шаги вводятся парами
«через сколько часов» + «текст»; пустая строка = шага нет, так он и
добавляется, и удаляется. Три места, где интерфейс предупреждает, а не
делает молча:

- **правка шагов у воронки, по которой идут люди** — позиция хранится
  НОМЕРОМ шага, а не текстом: вставка в середину даст ушедшим дальше чужое
  сообщение, обрезка хвоста завершит их цепочку досрочно. Число идущих
  показано над формой;
- **включение** — выключенная воронка безобидна, включённая пишет живым
  людям с первого же `/start`; воронку без шагов включить нельзя;
- **удаление** — вместе с воронкой пропадает история прохождений.

**Правка идёт по id, а не по имени.** Upsert по имени удобен для кода, но в
форме превратил бы переименование в создание второй воронки — и человек
молча оказался бы записан в обе.

**Удаление чистит запуски явно.** `ondelete="CASCADE"` в SQLite декоративен:
`PRAGMA foreign_keys` по умолчанию равен 0 (проверено). Без явной чистки
остались бы запуски в статусе «идёт» без воронки.

Миграция `0041_funnels`. Тесты: 21 + 19 на интерфейс.

### Исходная постановка F71 (для истории)
Подсмотрено у ManyChat, SaleBot, Typebot. Цепочки сообщений с задержками,
условиями и ветвлением по действию человека.

**Зачатки уже есть:** F45 (автоответчик и триггеры) и F46 (онбординг
новичка в личке) — это воронка без движка. Нужен слой, который позволяет
собирать такие цепочки без правки кода.

**Осознанно БЕЗ drag-n-drop конструктора.** У конкурентов визуальный
редактор — главный аргумент продажи, потому что их пользователь не
программист. Здесь пользователь — автор системы, и YAML или форма дадут тот

### F72 — Контент-календарь и согласование (РЕАЛИЗОВАНО 2026-08-15, СОГЛАСОВАНИЕ ПОЧИНЕНО 2026-08-16)

> **Настройка «редактор одобрил → ждём владельца» не делала ничего.**
> Цепочка была порвана сразу в двух местах: `mark_approved` — единственное
> место, где выставляется флаг ожидания, — не вызывался ниоткуда, а
> немедленная публикация флаг не проверяла (его смотрел только планировщик
> слотов).
>
> Опасность была не в поломке, а в ложной уверенности: владелец включал
> согласование, видел его в настройках и считал, что редактор без него
> ничего не опубликует. Публиковалось всё и сразу — и обойти согласование
> можно было просто выключив расписание.
>
> Теперь `approve_post` принимает, КТО одобряет: бот модерации разговаривает
> лично с владельцем и по умолчанию действует от его имени, а веб-админка
> подставляет роль из сессии. Сторож — `tests/test_owner_approval_gate.py`,
> и он проверяет, что публикация НЕ НАЧАЛАСЬ, а не что бот промолчал:
> первая версия теста была беззубой и падение диверсии не заметила.

**КАЛЕНДАРЬ НЕ ВРЁТ О БУДУЩЕМ — главное решение фичи.** Посты в этой системе
не привязаны к датам: они копятся одобренными и уходят пачкой в ближайший
слот (F11). Нарисовать «пост X выйдет в пятницу» нельзя — такой информации
нет, и придумывать её значило бы показать владельцу расписание, которого
система не исполняет. Поэтому:

- **прошлое — факты**: что и когда вышло;
- **будущее — обязательства**: посты с явной датой «не раньше» и
  забронированные рекламные места (F66);
- **очередь** — посты без даты показаны ЧИСЛОМ, а не размазаны по дням.

**Реклама и посты — на одной сетке.** Владелец планирует одну ленту, а не
две; разнеси их — и рекламный пост встанет в день, где уже стоит анонс,
потому что при планировании его не было видно.

**`scheduled_for` — это «не раньше», а не точное время.** Час по-прежнему
выбирают слоты и умное расписание; здесь только запрет выходить до срока.
NULL сохраняет прежнее поведение, поэтому обновление ничего не ломает.

**Согласование — флаг, а не новый статус.** Статус-машина F05 работает
годами; вносить в неё состояние ради НЕОБЯЗАТЕЛЬНОЙ проверки значило бы
рисковать публикацией ради церемонии. Публикатор просто не берёт посты с
`needs_owner_approval`. Настройка выключена по умолчанию: там, где владелец
работает один или доверяет редактору, согласование только замедляет.
Владелец никогда не подтверждает сам себя — это был бы тупик.

**РАЗНЫЕ ПРАВА НА ОДНОЙ СТРАНИЦЕ.** Календарь открыт редактору — планировать
контент его работа. Подтверждение живёт по адресу `/calendar/approve/...`,
который политика относит к владельцу; работает это за счёт правила
«побеждает самый длинный префикс» из F37. Без него редактор подтверждал бы
собственные посты, и согласование стало бы декорацией.

Кнопка подтверждения редактору не показывается вообще: предложить действие
и отказать в нём раздражает сильнее, чем отсутствие кнопки. Но объяснение,
почему её нет, показывается.

Миграция `0039_content_calendar`. Тесты: 18 + 12 роутовых. Две защиты
проверены на осмысленность: при снятии проверок в публикаторе падают два
теста (дата и согласование реально останавливают публикацию, а не рисуются
в интерфейсе), при удалении правила `/calendar/approve` — ещё один
(редактор начинает подтверждать сам себя).

### Исходная постановка F72 (для истории)
Подсмотрено у Postiz и Publer. Сетка публикаций на месяц, drag-n-drop
переноса времени, согласование поста до публикации.

**Блокируется F37.** Согласование без ролей бессмысленно: если все под одним
паролем, согласовывать не с кем. Делать строго после ролей.

### F73 — Публичный API и вебхуки (РЕАЛИЗОВАНО 2026-08-16)

Последняя фича бэклога. REST наружу с ключами и исходящие вебхуки на
события — связь с 1С, CRM и своим сайтом без правки кода.

**ПРОЕКТИРОВАЛОСЬ ОТ ОБРАТНОГО: не «что отдать», а «что нельзя отдать
никогда».** Чего в API нет и не будет:

- **секретов** — токенов ботов, ключей ИИ, session string. Ключ даёт доступ
  к ДАННЫМ, а не к учётным записям; иначе одна утёкшая строка отдавала бы
  вместе с ней все остальные системы владельца;
- **настроек.** Прочитать их — половина шага к тому, чтобы менять;
- **выгрузки людей.** CRM отдаёт СЧЁТЧИКИ: «сколько у меня подписчиков» —
  интеграция, «отдай список с контактами» — экспорт базы через ключ,
  лежащий в чужом репозитории;
- **удаления.** Область `write` умеет создавать и публиковать, но не
  стирать: ошибка в чужом скрипте не должна быть необратимой.

Обе границы закрыты тестами, которые читают саму схему API, а не список
разрешённого: новый метод с запрещённым словом в пути или с `DELETE`
уронит сборку.

**ЗАПИСЬ ВЕДЁТ В МОДЕРАЦИЮ, А НЕ В КАНАЛ.** Внешняя система не должна уметь
напечатать текст от лица канала одним запросом: ключ утекает вместе с чужим
репозиторием. Одобряет по-прежнему человек.

**КЛЮЧ ХРАНИТСЯ ХЭШЕМ И ПОКАЗЫВАЕТСЯ ОДИН РАЗ.** Утечка базы не должна
давать доступ. Поиск идёт по открытому префиксу (иначе пришлось бы сверять
хэш с каждой строкой), сравнение — `compare_digest`. Отзыв не удаляет
строку: стереть её значило бы убрать след использования ровно тогда, когда
он понадобился для разбора. Причина отказа не различается — «нет такого» и
«отозван» отвечают одинаково.

**SHA-256, А НЕ ARGON2, И ЭТО ОСОЗНАННО.** У паролей медленный хэш защищает
от перебора, потому что пароль выбирает человек. Здесь секрет — 32
случайных байта: перебирать бессмысленно при любой скорости, а медленный
хэш на КАЖДЫЙ запрос стал бы самой дорогой частью обработки.

**ОГРАНИЧЕНИЕ ЧАСТОТЫ СВОЁ У КАЖДОГО КЛЮЧА, «БЕЗ ПРЕДЕЛА» НЕ БЫВАЕТ.** Ключ
без ограничения превращает цикл без паузы в чужом скрипте в отказ
обслуживания для всей системы. Окно скользящее: при сбросе «раз в минуту»
можно отправить двойной предел на стыке. В ответе 429 обязателен
`Retry-After` — без него вызывающий начинает долбиться чаще.

Счётчик живёт В ПАМЯТИ ПРОЦЕССА. Это записанный предел: при нескольких
процессах предел размажется. Redis противоречит правилу проекта, а запись в
базу на каждый запрос дороже самого запроса.

#### Вебхуки

**ИСХОДЯЩИЕ, А НЕ ВХОДЯЩИЕ.** Принимать чужие вызовы система не умеет
намеренно — это была бы третья публичная поверхность со своей
аутентификацией, а исходящие закрывают исходную задачу без неё.

**ПОДПИСЬ ВКЛЮЧАЕТ МЕТКУ ВРЕМЕНИ.** Без метки перехваченный запрос можно
переслать повторно, и подпись останется верной навсегда. Секрет свой у
каждой подписки: общий означал бы, что один получатель может подделать
вызов к другому.

**ДОСТАВКА «ХОТЯ БЫ ОДИН РАЗ», И ЭТО НАПИСАНО В ТЕЛЕ.** Ответ мог
потеряться уже после того, как получатель всё сделал. В каждом событии есть
`event_id`; обещать «ровно один раз» было бы враньём — этого не умеет никто.

**ОТКАЗ СЧИТАЕТСЯ ОДИН РАЗ НА СОБЫТИЕ, А НЕ НА ПОПЫТКУ.** Очередь повторяет
задачу трижды; считая попытки, счётчик «отказов подряд» рос бы втрое
быстрее собственного названия, подписка умирала бы после трёх событий
вместо десяти, а владелец видел бы «10 отказов» там, где событий было три.
Поймано тестом при первом же прогоне.

**⚠️ АДРЕС ЗАДАЁТ ВЛАДЕЛЕЦ, И ЭТО ОРУЖИЕ.** Запрос уходит С СЕРВЕРА системы,
изнутри сети. Адрес `http://169.254.169.254/…` заставил бы её сходить в
метаданные облака и отдать наружу ключи собственного сервера — классический
SSRF. Внутренние и служебные адреса отклоняются, причём проверяется
РАЗРЕШЁННОЕ ИМЯ, а не текст: `internal.example.com` может указывать на
127.0.0.1. Полностью SSRF так не закрыть (имя перерезолвится к моменту
запроса), и это записано честно.

События: `post.published`, `member.joined`, `ad_request.created`,
`payment.received`. Список закрытый — «шлём всё подряд» означало бы, что
новое внутреннее событие однажды уедет наружу без чьего-либо решения.

Миграция `0047_api_and_webhooks`. Тесты: 89.

#### Исходная постановка (для истории)
Подсмотрено у ManyChat, Botpress, Chatwoot — их встраивают в чужие системы.

Сейчас веб-роуты обслуживают только собственную админку; подключить систему
к 1С, CRM или своему сайту без правки кода нельзя. Для автора, чей основной
профиль — интеграции (1С, ERP), это ограничение заметнее, чем звучит.

Нужны: REST наружу с ключами, вебхуки на события (пост опубликован, новый
участник, заявка рекламодателя, оплата), ограничение частоты. Проектировать
после F63 — API поверх несформированной модели данных придётся ломать.

### F74 — Mini App: витрина внутри Telegram (РЕАЛИЗОВАНО 2026-08-16)

Кабинет участника внутри Telegram: своя подписка, свои приглашённые,
партнёрский долг, каталог и таблица лидеров.

**СТЕК НЕ НОВЫЙ, И ЭТО ГЛАВНОЕ РЕШЕНИЕ ФИЧИ.** В постановке было записано
«новый фронтенд-стек» — от него отказались. React или Vue здесь означали бы
сборку, свой деплой и вторую систему шаблонов ради четырёх экранов, которые
уже умеет отдавать сервер. Взяты те же Jinja и тот же CSS, что во всей
админке, плюс переменные темы Telegram — мини-апп выглядит частью
мессенджера, а не сайтом внутри него. Если однажды понадобится живое
приложение с состоянием, стек добавится к работающему кабинету; наоборот —
нельзя.

**ДВА ЗАПРОСА ВМЕСТО ОДНОГО — не архитектурная прихоть.** `initData`
доступна только JavaScript внутри Telegram: в первом GET её физически нет,
и наполнить страницу сервер не может. Поэтому приходит пустая оболочка, а
содержимое запрашивается вторым запросом вместе с подписью.

**ПРОВЕРКА `initData` — ЕДИНСТВЕННАЯ ЗАЩИТА.** Без неё любой подставит чужой
`user.id` обычным curl и увидит чужой кабинет. Реализовано по описанию
Telegram: секрет = `HMAC(токен, "WebAppData")` — ключ строка, сообщение
токен, а не наоборот (перепутать местами — типовая ошибка, подпись тогда не
сходится никогда); сравнение только `compare_digest`, иначе подпись
подбирается побайтно по времени ответа; срок годности суток — подпись сама
не протухает, и перехваченная строка иначе осталась бы пропуском навсегда.
Причина отказа наружу НЕ раскрывается: «верна, но истекла» помогает
подбирать.

**ПЕРЕСМОТР МОДЕЛИ УГРОЗ, ЗАПИСАННЫЙ ЯВНО.** Это первая и единственная
публично доступная часть системы; всё остальное живёт за логином. Отличия
от «открыть админку наружу»:

- аутентификация — подпись Telegram, а не пароль и не ключ; подделать её
  нельзя, не зная токена бота, а токен наружу не выходит;
- сессии НЕТ намеренно: сессия живёт дольше подписи и пережила бы её
  протухание — то есть ровно та лазейка, которую срок годности закрывает.
  Подпись проверяется на каждый запрос;
- видно только своё. Единственное исключение — таблица лидеров, и оно
  осознанное: лидерборд без соперников бессмыслен, а видны там имя и очки,
  то есть ровно то, что человек и так видит в общем чате;
- ни один админский экран наружу не выведен.

Освобождение `/app` от проверки ролей проверено тестом на регрессию: ошибка
в префиксе открыла бы вместе с ним всю админку.

**Кнопки нет, пока не задан `MINIAPP_URL`** — мини-апп требует публичный
HTTPS-адрес. Пустой адрес честнее кнопки в никуда: человек считает поломкой
бота то, что просто не настроено. Проверяется и схема: Telegram молча не
откроет `http://` и localhost.

Тесты: 32 (17 на подпись, 15 на роуты).

#### Исходная постановка (для истории)
Подсмотрено у Telegram Web Apps API, tma.js, Mini Apps Builder, Telemetree.
Лидерборд викторин, реферальный кабинет, каталог магазина, личный кабинет
подписчика — в виде полноценного интерфейса, а не команд бота.

**Самая дорогая фича раздела: это новый фронтенд-стек, а не доработка.**
Плюс отдельная задача проверки `initData` на сервере — иначе любой сможет
выдать себя за другого пользователя.

Делать последней и только когда содержимое витрины уже существует: мини-апп
поверх пустоты показывать нечего.

### Архитектурные решения по P6 (приняты с владельцем 2026-08-15)

#### Решение 1: чтение А, но дорога в Б не закрывается
Строим под одного владельца с сотрудниками (F37), **но `tenant_id`
добавляется во все новые таблицы P6 сразу**, со значением 1 и NOT NULL.

Почему так, а не «потом добавим»: ключ арендатора на старте стоит одну
колонку, ретроспективно — миграция по всей базе плюс ревизия КАЖДОГО
запроса. Забытый фильтр в одном запросе означает показ данных чужого
арендатора; такую ошибку не ловит ни один тест, который не написан заранее.

**Что это НЕ значит.** Мы не делаем F27: ни изоляции, ни тарифов, ни
биллинга, ни Postgres. Только колонка и привычка её проставлять.
Старые таблицы F01–F51 не трогаем — их миграция станет частью F27,
если он вообще случится.

#### Решение 2: ОТМЕНЕНО 2026-08-15 — CRM читает данные Guardian напрямую

> **Отменено по факту, обнаруженному при реализации.** Исходное решение
> («Guardian публикует события, CRM их поглощает») опиралось на неверное
> утверждение, что базы контуров изолированы и связь между ними нужно
> строить. Проверка кода это опровергла:
>
> * `tg_repost/webui/guardian_routes.py` уже читает и ПИШЕТ `guardian.db`
>   напрямую, и в его докстринге это записано как осознанный выбор:
>   «отдельного API между ними заводить избыточно для однопользовательского
>   инструмента»;
> * зависимость идёт в ОБЕ стороны: `guardian/config.py` читает секреты из
>   БД `tg_repost`, `guardian/handlers/chat_member.py` импортирует
>   `targets_repo`.
>
> Базы разделены ради независимых цепочек миграций и раздельного деплоя, а
> не ради безопасности. **Настоящая граница — токены ботов**: компрометация
> токена Engage действительно не даёт прав модерации. Эта часть исходного
> обоснования верна, но к базам отношения не имеет.

**Что теперь.** CRM (F63) читает данные Guardian напрямую, как это уже
делает веб-админка. Механизма публикации и поглощения событий НЕ будет:
доставка, повторы и защита от повторной обработки — это постоянная
сложность ради задачи, которой нет.

**Что осталось в силе.** Append-only журнал ОПЕРАЦИЙ для денег
(F49/F67/F69/F70) по-прежнему нужен: вебхук об оплате приходит дважды, и
без идемпотентности человек получает доступ дважды. Но это внутреннее дело
`tg_repost`, а не связь контуров, и делается он в фазе 12, когда реально
понадобится, — а не заранее «на всякий случай».

**Урок на будущее:** проверять утверждение об архитектуре по коду ДО того,
как оно попадёт в решение. Это обоснование прожило в плане полдня и успело
определить содержание целой фазы.

#### Решение 3: очередь задач вместо второго планировщика
APScheduler остаётся для расписаний. Долгие операции (рассылка F64,
шаги воронок F71, повторы F55) идут через **таблицу-очередь с курсором**
и воркер в существующем процессе.

Redis и Celery НЕ вводим: устойчивость к рестарту даёт строка в БД, а не
брокер. Рассылка на 10 000 человек обязана продолжаться с места обрыва —
это свойство курсора, а не планировщика.

Один механизм на три фичи — строится один раз, до F64.

#### Решение 4: «по собеседнику» управляет токенами, а не каталогами
Семь фич P6 говорят с участником (F64, F67, F68, F69, F70, F71, F74) и по
принципу деления попадают в Engage.

**Ботов остаётся три.** Участнику нужен один `@бот`, а не четыре: четыре
токена — это четыре диалога в его списке чатов и вопрос «в каком из них
моя покупка». А вот пакет `engage/` делится на подпакеты по доменам.

#### Решение 5: F73 — это пересмотр модели угроз, а не роуты
В `webui/auth.py` записан осознанный трейдофф: CSRF-токенов нет, потому
что «нет сторонних origin» (cookie `samesite=lax` + доступ только с
localhost/VPN). **Публичный API убивает эту предпосылку.**

Значит F73 включает: ключи доступа, ограничение частоты, возврат CSRF для
UI-сессий, возможно вынос API в отдельный процесс. Это надо держать в
оценке фичи — иначе она кажется дешевле, чем есть.

### Что ещё ждёт решения владельца
1. **Маркировка против нативности** (F62) — продуктовое решение, не
   техническое. Пока не решено, кода не пишем.
2. **Нужен ли кросспостинг** (F39) — конкурировать с планировщиками на их
   поле или остаться узкими и глубокими.
3. **Когда Postgres.** При чтении А SQLite вытянет, но писателей
   становится больше: к listener, планировщику и вебу добавляются воркер
   очереди и обработчик платёжных вебхуков. Порог — не размер базы, а
   конкуренция за запись.

## P7 — Конструктор ботов (решения владельца 2026-08-17)

### F75 — Конструктор сценариев: граф вместо цепочки (РЕАЛИЗОВАНО 2026-08-17, шаги 1–6)

**Владелец переопределил решение по F71.** Там записано «линейные цепочки, без
ветвлений» с обоснованием «за ветвлением просят циклы, за циклами переменные,
и получается плохой язык программирования внутри админки». Запрос прямой:
нужен конструктор — любые типы шагов, с таймером и без, и выбор следующего
шага при верном и неверном ответе. Решение принято владельцем осознанно;
опасение остаётся в силе и закрывается не отказом, а тремя защитами (ниже).

Задача, из которой это выросло: **обучающий трек** — дать видео, задать
вопросы, по правильным ответам пустить дальше.

#### Четыре решения владельца

| Вопрос | Решение |
|---|---|
| Много сценариев в одном боте или много ботов | **Много ботов**, у каждого свои сценарии |
| Судьба линейных воронок F71 | **Заменить** конструктором, старые перевести миграцией |
| Интерфейс | **Сразу визуальный холст**, не список |
| Типы узлов в первом заходе | **Все** |

#### Что изучено у других

**Typebot** (открытый исходник) делит узлы на четыре категории, и деление
удачное — беру его: **пузыри** (показать), **ввод** (спросить и остановиться
до ответа), **логика** (фон, человек не видит), **интеграции** (наружу).
Ветвление у них — ОТДЕЛЬНЫЙ узел «условие» с двумя выходами, а не свойство
каждого узла; 12 операторов сравнения, склейка через И/ИЛИ. Узлы лежат в
группах, связи между группами — отдельные сущности.

**ChatbotX** отвечает на самую опасную проблему: правки идут в ЧЕРНОВИК, а
живые разговоры продолжаются на ОПУБЛИКОВАННОЙ версии; публикация
переключает, есть откат. Это ровно та беда, о которой в F71 стоит только
предупреждение в интерфейсе.

#### Модель

```
ManagedBot    бот: имя, токен (шифрованный), @username, включён
Flow          сценарий: бот, имя, триггер, черновик + опубликованная версия
FlowNode      узел: тип, настройки (JSON), координаты на холсте
FlowEdge      переход: откуда → куда + условие
FlowRun       прохождение: человек, текущий узел, ВЕРСИЯ сценария, переменные
```

**ПЕРЕХОДЫ ОТДЕЛЬНОЙ ТАБЛИЦЕЙ, а не полем `next_id` в узле.** У одного узла
выходов много: по кнопке, по варианту ответа, «иначе», «не ответил».
Отдельная таблица даёт и это, и рисование связей, и проверку графа одним
запросом.

**ПЕРЕМЕННЫЕ В ПРОХОЖДЕНИИ — то, без чего конструктор бесполезен.** Ответы
надо запоминать, иначе ветвиться не по чему.

#### Три защиты, без которых конструктор ломается

1. **Правка сценария, по которому идут люди.** Позиция человека — id узла;
   удалили узел, и человек в пустоте. Черновик и опубликованная версия;
   прохождение помнит СВОЮ версию и доигрывает по ней.
2. **Циклы и тупики.** Граф позволяет замкнуть узел на себя — бот засыплет
   человека сообщениями за секунды. Проверка перед публикацией
   (недостижимые узлы, узлы без выхода, цикл без выхода) плюс предохранитель
   на исполнении: не больше N переходов за один проход.
3. **Ожидание ответа навсегда.** У каждого «спросить» обязателен срок и
   ветка «не ответил», иначе прохождения зависают и копятся в базе.

#### Много ботов — БЕЗ многих процессов

aiogram ведёт несколько ботов одним диспетчером: `start_polling(*bots)`,
«one or more». Обработчик получает тот бот, которому пришёл апдейт. Значит
реестр ботов не требует ни отдельных контейнеров, ни вебхуков, ни разводки
апдейтов руками — один процесс Engage обслуживает все включённые боты.
Добавили бота — перезапускается задача опроса, тем же приёмом, что уже
сделан для бота модерации.

Токены — в шифрованной БД через админку, как все остальные секреты.

#### Холст без сборки — рекомендация по способу

Владелец выбрал визуальный холст; ЧЕМ его рисовать — вопрос открытый.
Предлагаю **свой редактор на обычном JS и SVG, без npm и без сборки**.
Причина: в проекте нет фронтенд-конвейера вовсе, и вносить его — это второй
стек, второй артефакт деплоя и npm внутри Python-образа. Узловой редактор с
перетаскиванием и связями — это порядка 600–800 строк обычного JS, что
дешевле, чем встроить сборку в контейнер, где её никогда не было.

React Flow даёт красивее из коробки, но платить за него придётся не строками,
а изменением всей упаковки проекта.

#### Порядок работ

| № | Шаг | Почему в этом порядке |
|---|---|---|
| 1 | Реестр ботов, токены в админке, много ботов одним процессом | Сценарию нужен владелец-бот |
| 2 | Модель графа + версионирование черновик/публикация | Без версий правка ломает идущих людей |
| 3 | Движок: показать / спросить / ждать / решить / сделать | 80% работы; холст без него не делает ничего |
| 4 | Проверка графа перед публикацией + предохранитель от циклов | Защита обязательна ДО того, как появится удобный редактор |
| 5 | Холст на своём JS | Поверх готового движка |
| 6 | Перевод старых воронок F71 в сценарии | Когда новое доказало работоспособность |

**Оценка честная: это больше, чем платежи целиком.** Не одна фича, а слой.

**Старое остаётся рабочим до шага 6.** Воронки F71 никто не выключает, пока
конструктор не пройдёт живую проверку: заменять работающее на непроверенное —
это то же, что копить непроверенные платежи, только с людьми внутри цепочек.

#### Что сделано (шаги 1–5)

| Что | Где | Ключевое решение |
|---|---|---|
| Реестр ботов | `managed_bots_repo`, `/bots` | Токен наружу не отдаётся ВОВСЕ: в объекте для шаблона поля нет, поэтому пустое поле при правке значит «не меняли» |
| Граф и версии | `flows_repo`, `flow_schema` | Правки в версию 0, публикация снимает неизменяемую копию; ссылки по `node_key`, а не по `id` |
| Проверка перед публикацией | `flows_repo.validate` | Несколько начал, недостижимые узлы, цикл без выхода, невозможное условие, два одинаковых выхода, незаполненное обязательное поле |
| Движок | `flow_engine` | Обход до первой остановки; предохранитель 25 шагов НА ИСПОЛНЕНИИ; тест кнопками, а не встроенным опросом |
| Живые боты | `flow_bots`, `flow_handlers`, супервизор | Один диспетчер aiogram на все боты реестра; только личка и только свой router; опрос перезапускается сразу после правки в админке |
| Холст | `/flows/{id}`, `static/flow_canvas.js` | Свой JS и SVG без сборки; схема полей приходит С СЕРВЕРА — вторая копия разошлась бы с движком |

**Тринадцать типов узлов** по пяти категориям: показать (текст, картинка,
видео, файл), спросить (кнопки, тест с проверкой, свободный текст),
подождать (пауза), решить (условие: 7 операторов), сделать (метка, очки,
доступ, вебхук).

**Семь условий перехода:** дальше, по кнопке (с точным значением или на
любую), верный ответ, неверный ответ, условие выполнено/не выполнено, не
ответил в срок.

#### Дыры, найденные при сборке движка и холста

Все — из запуска, а не из чтения кода:

* **пересланное сообщение сохраняет кнопки** — получатель пересылки двигал бы
  чужое прохождение, а сообщения летели бы тому, кто его начал. Теперь
  сверяется хозяин нажатия, и проверка стоит в движке, а не в обработчике:
  обработчиков будет больше одного, а забыть проверку достаточно в одном;
* **ответ одному боту уходил в прохождение у другого** — человек может
  проходить сценарии у двух ботов сразу, и оба могут ждать текст;
* **таймер сторожат два механизма** (задача очереди и подметание
  просроченных); второй сработавший закрывал прохождение на середине;
* **прохождение с выключенным ботом терялось** — просроченный срок был
  единственным признаком, по которому оно находилось, и сдвиг его стирал;
* **пройденный сценарий нельзя было пройти снова** — строка прохождения
  занята навсегда, человек пишет «/start» и получает тишину;
* **пояснение к верному ответу уходило тому, кто ошибся** — похвала за промах;
* **повреждённая на уровне байт запись секрета роняла процесс** — узкий
  перехват `InvalidToken` пропускал `binascii.Error`/`UnicodeEncodeError`;
  найдено в четырёх местах сразу (оверлей настроек, Guardian, реестр ботов,
  приём крипты), и самое дорогое из них — оверлей: он читается почти каждым
  модулем на импорте, то есть одна испорченная строка не давала подняться
  всей системе;
* **статика без метки версии** — браузер крутил прошлый скрипт холста, и
  палитра узлов не открывалась. Поймано глазами на живой странице;
* **палитра занимала 455 px из 812 на телефоне** — холст уезжал за экран.

#### Шаг 6: перевод воронок (сделано)

Кнопка «В конструктор» стоит прямо в строке воронки, бот выбирается там же.
Задержка становится узлом «пауза», сообщение — узлом «текст», порядок
сохраняется, сценарий публикуется сразу: черновик после переноса выглядел бы
готовым и никому не отвечал.

**Старая воронка НЕ выключается автоматически, и это главное ограничение.**
Выключение останавливает цепочку всем, кто сейчас внутри
(`handle_step_task` завершает запуск с причиной «воронка выключена»), поэтому
решение остаётся владельцу — вместе с числом людей, которым оно стоит
оборванной цепочки. Число показывается сразу после переноса.

**Перенос заодно лечит дефект, который в самих воронках не чинится.** Человек
попадает в воронку, нажав «Запустить» у бота Engage, а шаги ему отправляет
БОТ МОДЕРАЦИИ — другой токен. Telegram не разрешает боту заговорить первым,
поэтому тому, кто боту модерации никогда не писал, цепочка не доходит вовсе:
задача повторяется до предела и умирает в «failed», где владелец её не видит.
У сценария такой развилки нет по устройству: пишет тот бот, которому человек
написал сам.

Отказы переноса: воронка без шагов; у бота уже есть опубликованный сценарий
на «/start» (два сценария на один повод спорят за него); сборка не прошла
проверку графа — тогда откатывается всё, потому что половина сценария в
списке выглядит рабочей, а ею не является.

#### Чего ещё нет

* **живая проверка целиком.** Ни один сценарий ещё не отработал на реальном
  боте: токенов в системе нет. Проверено всё, что можно без Telegram —
  сборка, сохранение, отказ публикации, публикация, перенос воронки, обход
  графа, ветвление, сроки, предохранители.
* выравнивание узлов по сетке на холсте. Отмена действия (Ctrl+Z) и копия
  узла — сделаны.
