# Бэклог фич — Telegram Content Repost System

> Приоритет: `P0` = без этого не MVP, `P1` = сразу после MVP, `P2` = рост и
> монетизация, `P3` = идеи на будущее, не блокируют ничего.
> Каждая фича — отдельная задача для Claude Code, можно брать по порядку.
>
> **Статус фичи живёт В ЗАГОЛОВКЕ**, а не в теле раздела: `РЕАЛИЗОВАНО`,
> `ЗАКРЫТО через FXX`, `ПРОПУЩЕНО`, `идея, не задача`. Так «что не сделано»
> проверяется одной командой и не врёт:
>
> ```
> grep -E "^### F[0-9]+" FEATURES.md | grep -viE "РЕАЛИЗОВАНО|ЗАКРЫТО|ПРОПУЩЕНО|идея, не задача"
> ```
>
> До 2026-08-08 у F01–F23 статус лежал в теле, и эта проверка показывала
> реализованные фичи как незакрытые — риск, что новая сессия начнёт
> переделывать готовое. **Помечай статус тем же коммитом, что и код.**
>
> **2026-08-15 — цель проекта расширена владельцем.** Было: «личный
> инструмент на много групп». Стало: **один продукт, закрывающий все
> Telegram-задачи — ведение групп, ботов и бизнес-обвязку, и для бизнеса,
> и для личного использования.** Из-за этого:
>
> - добавлены разделы **P5** (F52–F62, заимствования из разведки рынка) и
>   **P6** (F63–F74, бизнес-обвязка);
> - **F37** переоткрыта — решение «пропустить роли» принималось под старую
>   цель и под новой больше не годится;
> - **F49** переписана: строим поверх Telegram Stars (0% комиссии), а не
>   поверх стороннего платёжного сервиса;
> - **F27** привязана к развилке А/Б (см. преамбулу P6) — от неё зависит,
>   закладывать ли multi-tenant в схему БД сейчас или никогда.
>
> Источник P5 и P6 — разбор 53 конкурирующих продуктов, август 2026.
> Таблицы: `Telegram-анализ-рынка-v2.xlsx` (рынок) и
> `Telegram-реализация-сравнение.xlsx` (наш код против конкурентов,
> с колонкой «проверено по коду» у каждой строки).
>
> На 2026-08-08 из F01–F51 не реализованы ровно две: **F27** (SaaS
> multi-tenant) и **F39** (кросспостинг). Всё из P5 и P6 — не начато.

## P0 — ядро MVP

### F01 — Управление источниками (РЕАЛИЗОВАНО)
Добавление/удаление/просмотр списка отслеживаемых Telegram-каналов.
Хранение в таблице `sources` (id, channel_username, channel_title, is_active,
added_at). Интерфейс — минимум CLI-команды, в идеале — Telegram-бот команды
(`/add_source @channel`, `/list_sources`, `/remove_source @channel`).

### F02 — Telethon listener (РЕАЛИЗОВАНО)
Подключение к Telegram через Telethon (юзер-сессия), подписка на новые
сообщения в источниках из `sources`. При получении нового поста — запись в
таблицу `posts` со статусом `new`, сохранение текста, медиа (путь к файлу),
ссылки на оригинал, timestamp.

### F03 — Фильтрация по ключевым словам (РЕАЛИЗОВАНО)
Опциональные списки стоп-слов и обязательных слов на канал или глобально.
Применяется сразу при получении поста, до сохранения в очередь (либо
сохраняется со статусом `filtered_out` для прозрачности — лучше второе,
чтобы видеть, что отфильтровалось и почему).

### F04 — Дедупликация (базовая, хэш) — РЕАЛИЗОВАНО
Хэш текста поста (нормализованный — без пробелов/регистра) для отсева точных
дублей между источниками. Простая и быстрая первая линия защиты, до
семантического дубль-чека из P1.

### F05 — Очередь постов (статус-машина) — РЕАЛИЗОВАНО
Таблица `posts` со статусами: `new → filtered_out | duplicate | rewriting →
rewritten → pending_approval → approved | rejected → posted | failed`.
Чёткие переходы, логирование каждой смены статуса с timestamp.

### F06 — Рерайт через OpenAI-совместимое API (РЕАЛИЗОВАНО)
Клиент с конфигурируемым `base_url`/`api_key`/`model`. Промпт-шаблон
(хранится в файле/БД, не хардкод) с инструкцией на уникализацию текста
с сохранением смысла. Сохранение результата в `posts.rewritten_text`.
Логирование стоимости запроса (токены) в БД для последующего учёта расходов.

### F07 — Ручное одобрение через Telegram-бота (РЕАЛИЗОВАНО)
Бот в личке владельцу присылает рерайченный пост с inline-кнопками
✅ Одобрить / ❌ Отклонить / ✏️ Редактировать. При "Редактировать" — бот
просит прислать новый текст, заменяет `rewritten_text`. Статус меняется
соответственно нажатой кнопке.

### F08 — Публикация в группу (РЕАЛИЗОВАНО)
При статусе `approved` — публикация поста (текст + медиа, если есть) в
целевую группу через Telegram Bot API. Обновление статуса на `posted`,
сохранение `message_id` опубликованного поста и timestamp.

### F09 — Конфигурация через .env + pydantic Settings (РЕАЛИЗОВАНО)
Все параметры (telegram api_id/api_hash, session string, bot token, target
group id, openai-совместимые ключи) — через `.env`, валидация через pydantic.

### F10 — Базовое логирование и обработка ошибок (РЕАЛИЗОВАНО)
Структурированные логи всех этапов пайплайна (получен пост → отфильтрован/
прошёл → рерайчен → отправлен на модерацию → опубликован/отклонён). Retry
с экспоненциальной задержкой для сетевых вызовов (Telegram API, LLM API).

## P1 — сразу после MVP

### F11 — Авто-постинг по расписанию (РЕАЛИЗОВАНО)
APScheduler-джоба, которая публикует посты со статусом `approved` (или сразу
`rewritten`, если включён режим без модерации) по расписанию — например,
каждые N часов, либо в заданные временные слоты. Переключается флагом
`auto_post_enabled` в конфиге, не требует пересборки.

### F12 — Несколько целевых групп (РЕАЛИЗОВАНО)
Таблица `target_groups` (id, chat_id, title, is_active). Поле в `posts` или
отдельная таблица `post_targets` — какие посты в какие группы идут (может
быть all/subset). UI выбора через бот-команды или конфиг по умолчанию.

### F13 — Семантический дубль-чек (эмбеддинги) — РЕАЛИЗОВАНО
Замена/дополнение хэш-дедупликации (F04) на эмбеддинги через тот же
OpenAI-совместимый API. Косинусное сходство между новым постом и постами
за последние N дней. Порог схожести — конфигурируемый. Хранение векторов —
можно в SQLite как BLOB или через расширение sqlite-vec, без необходимости
поднимать отдельную векторную БД на этом масштабе.

### F14 — Статистика и логи (просмотры, реакции) — РЕАЛИЗОВАНО
Сбор `view_count`/реакций по опубликованным постам через Telegram API (если
бот — админ группы, либо период опроса через Telethon). Таблица
`post_stats` с историей по времени (для построения трендов). Команда бота
`/stats` — сводка за период.

### F15 — Стиль-профили рерайта (РЕАЛИЗОВАНО)
Несколько промпт-шаблонов под тип контента (новость/мнение/инструкция/юмор).
Либо ИИ сам классифицирует входящий пост перед рерайтом (отдельный лёгкий
запрос-классификатор), либо привязка стиля к конкретному источнику в
конфиге `sources`.

### F16 — Поиск дополнительных источников (идея пользователя) — РЕАЛИЗОВАНО
Интеграция с Brave Search API. По ключевым словам из оригинального поста —
поиск 5-10 результатов, фильтрация на релевантность (можно через тот же
LLM — "выбери 2-3 наиболее релевантных из списка"), разделение на
русскоязычные и англоязычные. Добавление блока "Источники:" в конец
рерайченного поста со ссылками. Включается опцией на источник или глобально
(галочка "добор знаний").

### F17 — Антибан-механики (РЕАЛИЗОВАНО)
Рандомизация задержек между запросами Telethon (не молотить API без пауз).
Лимиты на количество чтений/действий в час. Конфигурируемые джиттер-интервалы.
Это must-have для стабильности, не просто "nice to have" — без этого юзер-
сессия рискует попасть под ограничения.

### F28 — Guardian настраивается по целевым группам (РЕАЛИЗОВАНО)
Галочка «использовать Guardian» стоит на каждой `TargetGroup` в `/targets`,
список защищаемых чатов синхронизируется в `guardian.bot_config`
(`protected_chat_ids`), и все хендлеры/джобы/антирейд работают по СПИСКУ
чатов, а не по одному. `GUARDIAN_GROUP_ID` остался только ради одноразовой
миграции старых данных. Guardian отдельно проверяет, реально ли он может
модерировать чат (`guardian_can_moderate`): владелец мог отметить цель, но
забыть выдать боту права администратора.

Исходная постановка (для истории): Guardian был жёстко
привязан к ОДНОЙ группе через `GUARDIAN_GROUP_ID` в `.env` — при этом
`target_groups` (F12) поддерживает несколько целей публикации. Если целей
несколько, Guardian реально защищал только одну из них. Нужна была галочка
"использовать Guardian" на каждой `TargetGroup` в `/targets`, и Guardian
должен уметь обслуживать N групп одновременно (один бот, несколько чатов —
не N ботов). Требует ревизии схемы Guardian (`members`/`warnings`/
`banned_users` и т.д. сейчас неявно на одну группу, нужен `chat_id` как
часть ключа везде) до реализации — см. отдельный анализ перед стартом.
Найдено на аудите ведения групп (2026-07-17), запрошено пользователем явно.

## P2 — рост и монетизация

### F18 — Авто-обложки для постов (РЕАЛИЗОВАНО)
Если у поста нет медиа — генерация изображения. Два пути: (а) через
локальный ComfyUI (у пользователя уже настроен ComfyUI + ZLUDA на RX 6600 в
других проектах — можно переиспользовать инфраструктуру) или (б) через
Unsplash API по ключевым словам темы поста (бесплатно, быстрее, но не
уникально). Конфигурируемый выбор стратегии.

### F19 — Умное расписание публикаций (РЕАЛИЗОВАНО)
На основе накопленной статистики (F14) — анализ, в какое время аудитория
активнее всего (по просмотрам в первый час после публикации). Автоматический
сдвиг времени публикации под пиковые часы. Нужно minimum 2-3 недели данных
перед тем как это включать осмысленно.

### F20 — Авто-дайджест (РЕАЛИЗОВАНО)
Раз в неделю (или другой период) — джоба, которая выбирает топ-N постов по
просмотрам/реакциям за период и собирает их в один сводный пост через LLM.
Публикуется отдельно от обычного потока.

### F21 — Нативная реклама в ленте (РЕАЛИЗОВАНО)
Каждый N-й пост (конфигурируемо) — рекламный, ИИ вписывает рекламный текст
органично в формат канала по заданному брифу. Ручное добавление рекламных
брифов через бота, статистика отдельно по рекламным постам.

### F22 — Growth-трекер (РЕАЛИЗОВАНО)
Корреляция прироста подписчиков канала (нужен сбор через Telegram API или
сторонние боты-аналитики типа TGStat API) с типом/источником постов.
Отчёт "что реально растит канал".

### F23 — Веб-UI поверх системы (шаг к SaaS) — РЕАЛИЗОВАНО
Простой веб-интерфейс (FastAPI + минимальный фронт, либо Streamlit для
быстрого старта — у пользователя уже есть опыт со Streamlit из проекта
Hedonism Wines) для управления источниками, очередью модерации, статистикой
без необходимости лезть в бота или БД напрямую. Это шаг к продукту, который
можно продавать другим владельцам каналов.

### F29 — Управление уже опубликованным постом (РЕАЛИЗОВАНО 2026-07-18)
Сейчас редактирование (`/moderation/{id}/edit`) работает только ДО публикации
(пока пост в очереди модерации). После `posted` пост неприкасаем из
админки — нельзя ни поправить текст (Bot API `edit_message_text`/
`edit_message_caption`), ни удалить (`delete_message`), ни закрепить/
открепить (`pin_chat_message`/`unpin_chat_message`). Частый сценарий
владельца канала: заметил опечатку/фактическую ошибку уже после публикации.

Реализовано веб-only (без кнопок в Telegram-боте — список из N целей на
пост неудобно рисовать inline-клавиатурой): новая таблица `PostTarget`
хранит результат публикации КАЖДОЙ цели (не только первой успешной, как
раньше), `/moderation/{id}` показывает список целей с кнопками
редактировать/удалить/закрепить-открепить по каждой отдельно.

### F30 — Модерация комментариев под постами канала (ЗАКРЫТО через F28)
Discussion-группа канала, куда Telegram зеркалит комментарии под постами —
это ОБЫЧНАЯ supergroup с точки зрения Bot API, Guardian её никак не
отличает от любой другой защищаемой группы. После F28 (Guardian настраивается
по целевым группам, не глобально) владельцу достаточно добавить
discussion-группу как цель (`/targets`) и включить галочку Guardian на ней —
капча/антиспам/варны/антирейд начинают работать над комментариями без
дополнительного кода. Отдельная реализация не нужна.

Также закрывает F36 (приветствие новых подписчиков канала) — единственный
реальный механизм приветствовать "подписавшегося" описан именно через эту
discussion-группу (см. F36 ниже), это тот же путь.

### F31 — Полный сбор метрик поста (реакции, форварды) (РЕАЛИЗОВАНО 2026-07-18)
`PostStat` в БД уже поддерживает `reaction_count`/`forward_count`, но
собирается сейчас только `view_count` (`scheduler/stats.py`). Реакции и
форварды физически доступны через Bot API/Telethon, просто не читаются.

Сбор теперь идёт по ВСЕМ целям публикации поста (через `PostTarget`, F29),
не только по первой, и суммируется в один `PostStat`-снимок на пост.

### F32 — Управление инвайт-ссылками и заявками на вступление (РЕАЛИЗОВАНО 2026-07-18)
Создание/отзыв/лимиты по инвайт-ссылкам целевых групп, одобрение/отклонение
заявок на вступление (join requests, если у группы включено подтверждение
администратором) — сейчас полностью вне системы, только руками в самом
Telegram.

Веб-страница `/invites`: создание/отзыв инвайт-ссылок (`InviteLink`),
список pending-заявок с кнопками одобрить/отклонить. Заявки также
дублируются владельцу в личку ботом с теми же кнопками (см.
`telegram/moderation_bot.py::_on_chat_join_request`).

## P3 — идеи на будущее (не блокируют разработку)

### F24 — Сравнение версий источников (РЕАЛИЗОВАНО)
Если источники на разных языках расходятся в трактовке темы — пометка поста
«есть разные версии события».

Реализовано в `enrichment/enricher.py::compare_source_versions` (промпт
`prompts/compare_sources.txt`): отдельный LLM-вызов, срабатывает ТОЛЬКО когда в
доборе (F16) нашлись источники обоих языков и включена настройка
`version_comparison_enabled` (по умолчанию выключена — это лишний платный
вызов). При расхождении в начало блока источников добавляется строка
«⚠️ Разные версии события: …».

### F25 — Авто-реакция на жалобы/негатив (РЕАЛИЗОВАНО)
Мониторинг негативных реакций на опубликованный пост, уведомление при
превышении порога, опциональное авто-удаление.

Реализовано в `scheduler/stats.py`: подсчёт негативных реакций при опросе
статистики, порог и авто-удаление настраиваются в /settings → «Реакция на
негатив», есть почасовой лимит авто-удалений (`max_auto_deletes_per_hour`),
чтобы всплеск негатива не выкосил ленту.

### F26 — Ротация между несколькими Telethon-сессиями (РЕАЛИЗОВАНО)
Балансировка чтения между несколькими юзер-сессиями — масштабирование числа
источников без риска для одного аккаунта.

Реализовано в `telegram/listener.py`: дополнительные клиенты поднимаются по
сохранённым сессиям (`TelethonSession`, страница /telethon-sessions), источники
распределяются между ними по кругу, у КАЖДОГО аккаунта свой почасовой лимит
«тяжёлых» действий (F17/F26). Общий прокси на все клиенты (см. `proxy.py`).

### F27 — SaaS multi-tenant архитектура (ЖДЁТ РЕШЕНИЯ ПО РАЗВИЛКЕ А/Б)
Полноценный переход от "система для одного владельца" к multi-tenant
продукту с отдельными аккаунтами, биллингом, изоляцией данных между
клиентами. Это отдельный по объёму проект поверх текущего ядра, не задача
на ближайшие месяцы.

**2026-08-15.** Нужность F27 целиком зависит от развилки из преамбулы P6:
- **чтение А** (мой бизнес + мои личные каналы, один владелец, сотрудники) —
  F27 НЕ нужен никогда, хватает F37;
- **чтение Б** (продавать доступ другим компаниям) — F27 обязателен.

**Решать надо СЕЙЧАС, а не когда дойдут руки.** Ключ арендатора
(`tenant_id`) добавляется в схему на старте почти бесплатно, а
ретроспективно — это миграция по всем таблицам разом, с переписыванием
каждого запроса и риском утечки данных между арендаторами на любом
забытом фильтре. Пока таблиц ~30, цена решения низкая; после P6 их будет
вдвое больше.

### F33 — Опросы (polls) в ленте (РЕАЛИЗОВАНО 2026-07-18)

### F40 — Редакция из двух агентов: профессиональный рерайт (РЕАЛИЗОВАНО 2026-08-01)
Раньше рерайт был «в один присест»: модель писала пост начисто, никто его не
правил — отсюда слабый, местами выдуманный текст. Теперь тот же клиент играет
ДВЕ роли (`rewriter/editorial.py`):

1. **Журналист** пишет черновик по источникам (персона усилена: журналист с
   20-летним опытом).
2. **Редактор-фактчекер** сверяет черновик с источниками (исходный пост +
   статья по ссылке), пишет пронумерованные замечания и вердикт OK/ПРАВИТЬ,
   помечает спорные факты на веб-сверку.
3. **Веб-сверка** помеченных фактов через тот же поиск, что F16 (SearXNG/
   Brave); находки идут журналисту.
4. **Журналист переписывает** по замечаниям и находкам. Цикл — до вердикта OK
   или до `editorial_max_rounds`.

Замечания редактора сохраняются на варианте (`PostRewriteVariant.editorial_notes`,
миграция 0023) и показываются при модерации. По умолчанию ВКЛ, 1 раунд; всё —
настройками в /settings → «Редакция из двух агентов». Дороже по токенам: 1 раунд
= 3 вызова LLM на вариант, поэтому под выключателем. 402/ошибка баланса на любом
шаге останавливает пачку (посты остаются `new`); прочие сбои рецензии/правки не
теряют хороший черновик.

## P4 — Вовлечение аудитории: боты-помощники админа (F41–F49)

Запрос владельца 2026-08-01: нужны дополнительные обслуживающие боты —
геймификация, приглашения с указанием источника рекламы, конкурсы, «и что там
ещё надо админам групп». Ниже — результат разбора, что реально нужно и что
физически позволяет Telegram Bot API.

### Архитектурное решение: куда что класть

Три процесса вместо двух, с чётким разделением по СОБЕСЕДНИКУ:

| Процесс | С кем говорит | Зона ответственности |
|---|---|---|
| Репост-бот (есть) | владелец | публикация, модерация контента |
| Guardian (есть) | группа | защита: капча, антиспам, варны, антирейд |
| **Engage (новый)** | **участники** | квизы, конкурсы, рефералы, предложка, онбординг |

**Итого три бота.** Разделены по СОБЕСЕДНИКУ, а не по фичам — это и есть
причина, по которой третий бот действительно нужен, а не «ещё один процесс ради
процесса»:

- Репост-бот — приватный инструмент владельца (кнопки одобрения постов, статистика).
- Guardian — «полицейский» в группе, участники с ним не разговаривают.
- Engage — публичный, дружелюбный: участники пишут ЕМУ в личку, deep-link
  рефералки ведёт на НЕГО, он же ведёт квизы и конкурсы. Смешивать его с
  «ботом владельца» — плохой UX (подписчик видит чужие админ-кнопки) и лишняя
  поверхность атаки.

**Важно: Engage НЕ читает поток сообщений группы.** Ему это не нужно — квиз
работает по схеме «бот спросил → участник нажал кнопку → `poll_answer`».
Значит, не нужен privacy mode off, не нужно дублировать трафик Guardian'а и не
растут риски по лимитам Telegram. Это следствие правильно выбранной механики
(см. F43): если бы очки давались за сообщения, второй читатель потока был бы
неизбежен.

### Что Telegram реально позволяет (сверено с Bot API)

- **`ChatMemberUpdated.invite_link`** и **`ChatJoinRequest.invite_link`** — при
  вступлении Telegram САМ сообщает, по какой ссылке пришёл человек. **Эти данные
  нам уже приходят в существующие хендлеры, но мы их не сохраняем** — отсюда F41,
  самая дешёвая и самая полезная фича блока.
- **Deep-link `t.me/<bot>?start=<payload>`** (payload до 64 символов) — основа
  реферальной программы: по нему бот узнаёт, кто пригласил.
- **`getChatMember(chat_id, user_id)`** — проверка «подписан ли» для условий
  конкурса. Требует, чтобы бот был админом в проверяемом чате.
- **`sendDice`** — нативный рандом Telegram (кубик/дартс), годится для
  наглядного публичного розыгрыша «на глазах у зрителей».
- **Ограничение:** в КАНАЛАХ у постов нет авторов-участников — бот не видит, кто
  что написал. Геймификация по активности работает только в ГРУППАХ, включая
  discussion-группу канала (что для канала и есть рабочий вариант).
- **Нет события «подписался на канал»** — у ботов такого апдейта не существует
  (уже упиралось в F36). Прирост канала считаем по `getChatMemberCount`, а
  поимённо — только по вступлениям в группу.

### F41 — Атрибуция подписчиков: откуда пришёл (РЕАЛИЗОВАНО 2026-08-06)
Продолжение F32. Сейчас инвайт-ссылки создаются и отзываются, но **никто не
знает, какая из них сколько привела** — данные от Telegram выбрасываются.

Сохранять `invite_link` при вступлении (`chat_member`) и в заявке
(`chat_join_request`) → поле в `JoinRequestRecord` + новая таблица
`MemberOrigin` (chat_id, user_id, invite_link_id, joined_at, left_at).
На `/invites` — колонки «пришло / осталось сейчас / отвалилось / retention 7д и
30д». Плюс поле «стоимость размещения» у ссылки → **CPA, цена подписчика**.

Это замыкает контур с F35 (учёт рекламного дохода) с другой стороны: F35 — что
заработали на рекламе у себя, F41 — что потратили на рекламу себя и что это
принесло.

### F42 — Реферальная программа для участников (РЕАЛИЗОВАНО 2026-08-06)
Участник пишет боту Engage → получает персональную ссылку
`t.me/<bot>?start=ref_<user_id>` (или персональную инвайт-ссылку группы) →
система считает, кого он привёл и кто из них остался. Лидерборд рефереров,
награды за пороги (N приглашённых → роль/бейдж/приз). Защита от накрутки:
приглашённый засчитывается только если прожил в группе > N дней и написал хотя
бы одно сообщение.

### F43 — Геймификация: контент → вопрос → очки (РЕАЛИЗОВАНО 2026-08-06)
**Механика владельца (уточнено 2026-08-01):** бот САМ выдаёт контент, а через
время задаёт по нему вопрос. Ответил верно — очки.

Это принципиально лучше «очков за сообщения»: те превращаются в ферму флуда
(люди пишут «+», «ок», чтобы набить счётчик), а здесь очки даются за то, что
человек реально прочитал материал. И механика самодостаточна: не требует, чтобы
в группе кто-то что-то писал — бот сам создаёт повод.

**Почему это ложится на нашу систему почти без работы:** у нас уже есть полный
текст статьи (trafilatura, F16), готовый пост и редактор-фактчекер (F40),
который эти факты проверил. Составить из проверенного материала вопрос с
вариантами ответа — ОДИН дополнительный LLM-вызов. Вопрос гарантированно
основан на реальном тексте, а не на выдумке модели.

Схема:
1. Пост опубликован обычным пайплайном.
2. **Составитель квиза** (новая LLM-роль) делает из статьи вопрос + 3–4 варианта
   ответа, один верный, плюс короткое пояснение со ссылкой на источник.
3. Через настраиваемую паузу бот Engage публикует вопрос в группу как
   **quiz-poll** (`sendPoll(type="quiz", correct_option_id=...)`).
4. Очки за правильный ответ, бонус за скорость и за серию дней.
5. Уровни/бейджи, `/me`, `/top` (день/неделя/месяц), авто-пост лидерборда.

**Почему quiz-poll, а не свободный ответ:** Telegram нативно поддерживает
викторину — сам проверяет правильность, показывает верный вариант с пояснением
и не даёт переголосовать. Это ноль LLM-вызовов на проверку ответов и ноль
споров «я вообще-то это и имел в виду». Свободные ответы с LLM-проверкой —
возможное расширение потом, но дороже и спорнее.

Очки начисляются также за приведённого реферала (F42) и участие в конкурсе
(F44). Настраивается на чат, выключается одной галочкой.

**Ограничение:** публиковать вопрос и видеть ответы бот может только в ГРУППЕ
(в канале нет участников-авторов) — для канала это его discussion-группа.

### F44 — Конкурсы и розыгрыши (РЕАЛИЗОВАНО 2026-08-06)
Создание конкурса в веб-админке: период, приз, число победителей, **условия
участия** (подписан на канал(ы) — проверка `getChatMember`; состоит в группе;
минимум N очков F43; привёл N рефералов F42). Участие — кнопкой под постом
конкурса. По окончании: проверка условий у всех записавшихся, честный розыгрыш
и автообъявление победителей с упоминанием.

**Прозрачность розыгрыша** (иначе аудитория не верит): seed фиксируется заранее
и публикуется вместе с алгоритмом, чтобы любой мог перепроверить результат;
опционально — публичный `sendDice` для наглядности. Полный протокол розыгрыша
сохраняется в БД.

### F45 — Автоответчик и триггеры по ключевым словам (РЕАЛИЗОВАНО 2026-08-06)
Частые вопросы («как купить», «где правила», «когда стрим») → авто-ответ по
ключевым словам с антиспам-защитой (не чаще раза в N минут на чат, не отвечать
самому себе). Снимает с админа рутину. Технически — ложится в Guardian, он уже
разбирает каждое сообщение по фильтрам.

### F46 — Онбординг новичка в личке (РЕАЛИЗОВАНО 2026-08-06)
Guardian уже капчит и приветствует В ГРУППЕ. F46 — следующий шаг: Engage пишет
новичку В ЛИЧКУ (если тот стартовал бота) короткий онбординг — правила, что тут
есть, полезные ссылки, кнопка «показать топ участников». Конверсия «вступил →
остался» заметно выше, когда человека встретили.

### F47 — Предложка: посты от подписчиков (UGC) (РЕАЛИЗОВАНО 2026-08-06)
Участник шлёт пост боту Engage → тот кладёт его **в ту же очередь модерации**,
что и рерайты (`PostKind.UGC`, статус `rewritten`) → владелец одобряет в боте
или веб-админке → публикуется с указанием автора. Красиво переиспользует весь
существующий пайплайн модерации/публикации: новый только источник поступления.

### F48 — Служебная гигиена группы (РЕАЛИЗОВАНО 2026-08-06)
Пакет мелких, но раздражающих-в-отсутствие вещей:
- авто-удаление служебных сообщений («вошёл в группу», «закрепил сообщение»);
- ночной режим: авто-включение slow mode / закрытие группы на ночь и открытие
  утром (у Guardian уже есть «тихие часы» — расширить до действий);
- напоминание правил по расписанию;
- авто-закрепление важного поста после публикации.

### F50 — «Редакционная кухня»: живая трансляция диалога агентов (РЕАЛИЗОВАНО 2026-08-06)
Запрос владельца 2026-08-01: «хочу видеть, что копирайтер с редактором
обсуждают и что переписывают».

**Что важно понимать про природу этих «ботов»:** журналист и редактор — не
отдельные Telegram-боты, а LLM-роли внутри одного процесса
(`rewriter/editorial.py`), они не «переписываются», а вызываются
последовательно. Делать из них настоящих ботов, которые шлют друг другу
сообщения через Telegram, — это добавить сетевые задержки, лимиты и точки
отказа ради театральности. **Но показать их обмен как живой диалог — можно и
нужно, и это почти бесплатно:** мы просто транслируем то, что и так происходит.

Как это выглядит: отдельный чат «редакционная кухня» (приватная группа или
канал — только для владельца), куда по каждому посту приходит цепочка,
связанная реплаями:

```
📝 Журналист · пост #123 · черновик
   [текст черновика]
   └ 🔍 Редактор · ВЕРДИКТ: ПРАВИТЬ, 3 замечания
        1. Выдумана цифра «50% рынка» — в источниках её нет
        2. Слабый лид: начинается с «в последнее время»
        3. Не убрана ссылка на канал автора
      └ 🌐 Проверка фактов · сверено 2 утверждения
           • «крупнейший банк 2025» → расходится, см. example.com/a
        └ ✍️ Журналист · правка готова
             [итоговый текст]
          └ ✅ Редактор · одобрено. 1 раунд, 4 200 токенов
```

**Техническое решение (важно для чистоты слоёв):** `rewriter/editorial.py` НЕ
должен ничего знать про Telegram — сейчас он не импортирует ни бота, ни БД, и
это стоит сохранить. Поэтому в `editorial_rewrite()` добавляется необязательный
callback `on_step(stage, text)`, а связывает его с ботом уже
`scheduler/jobs.py`. Тогда та же трансляция без переделок уходит и в веб-панель
(SSE-поток `/logs` уже есть, см. `webui/log_broadcast.py`), и в тесты (callback
подменяется списком).

Отдельный бот НЕ нужен — шлёт существующий репост-бот.

Настройки:
- `editorial_newsroom_enabled` — включить трансляцию;
- `editorial_newsroom_chat_id` — куда (можно поставить свой user_id и получать
  в личку, но **не рекомендуется**: 4–5 сообщений на пост забьют ту же личку,
  где кнопки одобрения);
- `editorial_newsroom_verbosity` — `all` (весь ход) / `problems` (только когда
  редактор нашёл замечания) / `summary` (одна строка-итог на пост).

**Предупреждение по объёму:** при пачке в 5 постов за тик и `all` это ~25
сообщений за тик. Поэтому режим по умолчанию — `problems`: молчит, когда всё
хорошо, и показывает разбор, когда редактор реально что-то нашёл. Длинные
тексты режутся существующим `_clip` (UTF-16-корректная обрезка под лимит
Telegram 4096).

**Зачем это на самом деле нужно** (не только «интересно посмотреть»): это
инструмент отладки качества. Когда рерайт выходит плохим, сейчас видно только
результат — а причина может быть в чём угодно: статья не скачалась, редактор
придрался не к тому, промпт кривой. Живой ход разговора показывает, на каком
шаге всё пошло не так, и позволяет чинить конкретный промпт, а не гадать.

### F49 — Платный доступ и подписка (СКОУП ПЕРЕПИСАН 2026-08-15)
Монетизация закрытого канала: оплата через Telegram Stars → автовыдача
инвайт-ссылки с ограничением, авто-кик по окончании подписки, продление.
Отдельный крупный кусок с платёжным контуром и юридическими вопросами —
записано, чтобы не потерялось, но не в ближайшую очередь.

**Пересмотрено после разбора экономики рынка.** Ставка на Stars,
записанная выше «на глазок», подтвердилась цифрами и стала главным
аргументом, а не деталью:

| Способ | Комиссия |
|---|---|
| **Telegram Stars** | **0%** — Telegram не берёт ничего |
| Bot Payments API | 0% Telegram + 2.8–3.9% провайдеру |
| Tribute | 10% |
| PaidSub.io | 15% |
| Paywall.pw | 20% |

Единственный вычет у Stars — 30% Apple/Google (15% при доходе <$1M/год),
и ТОЛЬКО когда пользователь покупает звёзды через мобильный стор; при
пополнении с Desktop/Web его нет. Вывод в TON через Fragment, доступен
через 21 день после получения звезды.

Дополнительно: с 2024 Stars ОБЯЗАТЕЛЬНЫ для продажи цифровых товаров в
ботах и мини-аппах — обход через обычный эквайринг ведёт к бану бота.

**Что делаем мы, а что Telegram.** Платёжный контур — Telegram (подписка
включается в настройках канала, автосписание каждые 30 дней, доступ
держится до конца оплаченного периода). Наша часть — автоматизация
выдачи и снятия доступа, привязка к CRM (F63), сегментам (F64) и
аналитике. То есть нам не хватает не «приёма денег», а обвязки поверх
него — и это ровно то, что мы умеем.

Точный процент разработчика зафиксирован в ToS 6.2.4 — сверить перед
запуском, извлечь его в ходе разведки не удалось.

### F51 — Сюжеты: одна новость из нескольких источников (РЕАЛИЗОВАНО 2026-08-07)

**Проблема пользователя:** источников много, одна и та же новость приходит из
нескольких и публикуется повторно.

Отдельная «БД новостей» не понадобилась — она уже есть (`posts`). Не работали
два имеющихся слоя дедупа, каждый по своей причине:

1. **Дыра в RSS.** `rss/poller.py` считал `content_hash`, клал его в базу и
   НИ РАЗУ не сверял; семантического дубль-чека там не было вовсе.
   `_known_guids` её не закрывает — он сравнивает guid ВНУТРИ одной ленты.
   Для ИБ-новостей это било сильнее всего: одна CVE из пяти лент = пять
   постов и пять оплаченных рерайтов.
2. **Семантика была выключена** по умолчанию, а хэш ловит только буквальный
   копипаст: разные редакции пишут об одном событии своими словами.

**Решение — не заплатка.** Дыра появилась потому, что правила приёма
скопировали в две ветки и в RSS-копию половину проверок не перенесли. Приём
вынесен в `tg_repost/ingest.py`; у вызывающих осталось только то, что у них
действительно различается — чем опознаётся «уже видел это» (Telegram:
`message_id`, RSS: `guid` ленты).

**И смысл дубля перевёрнут.** Повтор из НЕЗАВИСИМОГО источника — не мусор, а
подтверждение: ровно на нём работает редактор-фактчекер (F40) и сравнение
версий (F24). Семантический повтор больше не исчезает, а цепляется к первому
пришедшему посту в сюжет (`story_clusters`). Публикуется по-прежнему один
пост; остальные живут при нём источниками и уходят в фактчек.

Буквальный копипаст по хэшу в сюжет НЕ идёт: считать его «вторым источником»
значило бы врать редакции о числе подтверждений.

**Настройки** (`/settings` → «Дубли и сюжеты»): семантика теперь ВКЛ по
умолчанию, порог 0.88 (было 0.92 — пропускал половину реальных повторов),
окно сравнения 3 дня, пауза на сбор сюжета `cluster_grace_minutes` (по
умолчанию 0 — это прямая задержка публикации, включать осознанно).

**Ограничения, про которые стоит помнить:**
- база сравнения наполняется постепенно: у постов, набранных при выключенной
  семантике, эмбеддинга нет, и первые дни повторы ещё будут проскакивать;
- в промпт уходит максимум 4 источника по 1500 символов — сюжет из десяти
  лент иначе раздул бы счёт за токены без пользы;
- `primary_post_id` намеренно без ForeignKey: пара FK с `posts.cluster_id`
  замкнула бы цикл, на котором падает `create_all` (SQLite не умеет
  `ALTER ... ADD CONSTRAINT`).

### Что НЕ вошло и почему
- **Приветствие подписчиков канала поимённо** — Bot API физически не даёт
  события подписки на канал (см. F36, закрыто через discussion-группу).
- **Учёт кросс-промо с другими каналами** — по сути ручной журнал, покрывается
  F35 (журнал дохода) и F41 (атрибуция) без отдельной фичи.
- **Собственный анти-бот-скоринг** — уже есть в Guardian (G10 гибридный режим +
  G15 анализ профиля).

### F52 — `is_premium` как сигнал доверия (РЕАЛИЗОВАНО 2026-08-15)
Подсмотрено у Safeguard. Поле `is_premium` приходит в апдейтах Telegram
бесплатно и не требует ни одного лишнего запроса — а мы не использовали его
нигде (греп до реализации: 0 вхождений).

Давний Premium-аккаунт проходил капчу наравне с созданным час назад, хотя у
скам-ботов платной подписки обычно нет.

**Реализация.** `is_premium` — единственный сигнал В ПОЛЬЗУ участника в
`compute_profile_score` (G15): уменьшает сумму на `PREMIUM_TRUST_BONUS` (2 —
столько же, сколько даёт подозрительная био, то есть гасит ровно один
сильный негативный сигнал, а не все сразу). Результат ограничен снизу нулём:
иначе чистый Premium-профиль уходил бы в минус и «заносил» отрицательный
запас на будущие проверки, превращая смягчение в фактический пропуск капчи.

`PREMIUM_TRUST_ENABLED` по умолчанию **выключен** — это ослабление защиты, а
Premium ПОКУПАЕТСЯ: мотивированный спамер оплатит подписку и обойдёт
смягчение. Поэтому сигнал в общий скоринг, а не пропуск проверки.

**Отклонение от первоначальной записи:** здесь было «настройка на группу».
Сделано глобальной — `profile_suspicion_threshold` и все прочие настройки
капчи в `guardian/config.py` глобальные, и заводить пер-чатовый механизм
ради одного флага значило бы держать в системе два разных способа
настраивать одно и то же. Пер-чатовые списки (F28) остаются пер-чатовыми.

Тесты: 5 новых в `tests/test_guardian_profile_analyzer.py`. Отдельно
проверено, что защитный тест «выключено — значит не влияет» реально падает
при закороченном флаге, а не зелёный по случайности.

### F57 — Петля обучения антиспама  ⭐ ГЛАВНЫЙ РЫЧАГ
Подсмотрено у tg-spam (umputun): спорные вердикты уходят в очередь с
кнопками «спам / не спам», и каждое решение модератора делает классификатор
точнее именно на этой аудитории.

**Наша проблема названа прямо в коде.** `guardian/filters/ai_filter.py:53-88`

фильтр не становится точнее НИКОГДА, и владелец даже не узнаёт, что тот
ошибся.

Делаем: спорные случаи (низкая уверенность, таймаут, невалидный ответ) —
в очередь, показать владельцу с кнопками, решения копить как обучающую
выборку и подмешивать few-shot примерами в промпт. Без переобучения модели:
few-shot из своих же примеров даёт основной эффект за долю усилий.

### F62 — Маркировка рекламы: ОРД и erid (ТРЕБУЕТ РЕШЕНИЯ ВЛАДЕЛЬЦА)
Не заимствование у конкурента, а требование закона РФ. Реклама должна нести
erid-токен от оператора рекламных данных, пометку «Реклама» с указанием

**Единственный пункт всего бэклога, где цена бездействия — штраф, а не
упущенная выгода.** У нас ЕСТЬ нативная реклама (F21) и учёт дохода (F35) —

**Почему это не задача разработчику, а решение владельца.** Маркировка по
смыслу противоречит F21: нативная реклама работает ровно потому, что не
выглядит рекламой, а обязательная пометка её обнажает. Технически задача
несложная — поле `erid` на пост, пометка в шаблоне, выгрузка отчёта. Но
сначала нужно решить, что делать с нативностью, а уже потом писать код.

Штрафы по ст. 14.3 КоАП для юрлиц измеряются сотнями тысяч рублей;
законодательство менялось несколько раз — суммы и порядок сверить перед
запуском, не полагаться на цифры из этого файла.

## P6 — бизнес-обвязка: продукт «всё в одном» (F63–F74)

> **Зачем этот раздел.** По контенту мы сильнее рынка: двухагентная редакция
> (F40) и сюжеты (F51) не встречаются НИ У ОДНОГО из 53 разобранных
> продуктов. По бизнес-обвязке — пусто: ни денег, ни CRM, ни поддержки, ни
> команды. То есть у системы отличный редакционный конвейер, но нет ничего,
> что превращает аудиторию в выручку.
>
> ⚠️ **РАЗВИЛКА, БЕЗ КОТОРОЙ НЕЛЬЗЯ ПРОЕКТИРОВАТЬ СХЕМУ БД.**
> «Для бизнеса» читается двумя способами, и они ведут к разной архитектуре:
>
> | | Что это значит | Что нужно | Объём |
> |---|---|---|---|
> | **А** | Мой бизнес + мои личные каналы. Один владелец, возможно сотрудники | F37 (роли). **F27 НЕ нужен** | Реально за месяцы |
> | **Б** | Продавать доступ другим компаниям | Всё из А + F27, изоляция данных, тарифы, биллинг, Postgres | Другой продукт, ×5 |
>
> **Всё в P6 одинаково для обоих чтений** — работа не блокируется. Но
> `tenant_id` в схеме на старте стоит копейки, а ретроспективно это миграция
> по всем таблицам с риском утечки между арендаторами на каждом забытом
> фильтре. Решить до начала F63, потому что F63 — фундамент остальных.
>
> **Порядок внутри P6 не произволен:** F63 → F64 → всё остальное. Рассылка
> без сегментов бессмысленна, сегменты без карточки участника не из чего
> строить.

### F63 — CRM участника: карточка, теги, сегменты  🔑 ФУНДАМЕНТ P6
Подсмотрено у ManyChat, SaleBot, BotHelp — там это ядро продукта.

**Данные у нас уже есть, карточки нет.** F41 знает, откуда человек пришёл,
F42 — кто его привёл, F43 — насколько он активен, Guardian — как он себя
ведёт. Но `UserActivity` (`db/models.py:855`) хранит только очки, а
сегментации нет вообще (греп `segment|сегмент` даёт лишь HTML-теги
Telegraph и строки локализации).

Делаем: единая карточка человека — история, источник прихода, активность,
покупки, теги (ручные и автоматические), сегменты как сохранённые запросы.

**Главный архитектурный вопрос этой фичи:** участник живёт сразу в трёх
контурах — `tg_repost` (посты), `guardian.db` (модерация), `engage` (очки).
У Guardian СВОЯ база и своя цепочка миграций. Единая карточка требует
решить, где хранится человек и как контуры на него ссылаются, не ломая
изоляцию Guardian. Обсудить до начала работ.

### F64 — Рассылки по сегменту
Подсмотрено у ManyChat и BotHelp. Broadcast с таргетом по тегу, активности,
источнику прихода или факту покупки.

Без этого F63 бесполезна: сегменты нужны, чтобы по ним что-то делать.
Греп `broadcast` показывает только SSE-логи админки и трансляцию редакции
(F50) — рассылок участникам нет.

Обязательно с ограничениями: лимиты в секунду, пауза между отправками,
обработка блокировок бота, отписка одной кнопкой. **Лимитер переиспользуем
из F17** (антибан-механики), а не пишем второй — иначе два независимых
регулятора будут спорить за одну и ту же квоту Telegram.

### F65 — Медиакит и отчёт рекламодателю
Подсмотрено у LiveDune и TGStat. Автоотчёт по каналу: охваты, ERR (F53),
динамика подписчиков, лучшие посты, портрет аудитории — в PDF или на
странице по ссылке.

Самая дешёвая фича блока: **все данные уже собраны**, нужен только шаблон и
экспорт. При этом продавать рекламу без медиакита практически невозможно —
рекламодатель просит его первым же сообщением.

### F66 — Приём заявок рекламодателей и бронь мест в сетке
Подсмотрено у Telega.io. Форма или бот-диалог для рекламодателя, календарь
занятости рекламных слотов, статусы заявки, автоматический учёт дохода.

У нас уже есть F21 (нативная реклама) и F35 (журнал дохода) — не хватает
входа заявки и календаря. Связано с F62: если решение по маркировке принято,
erid запрашивается на этом же шаге.

### F67 — Affiliate: деньги поверх реферальной программы
Подсмотрено у InviteMember, где партнёрский движок — ключевая фича.

**F42 уже сделал сложную часть** — антифрод: реферал подтверждается только
если приглашённый вступил, написал и прожил N дней. Осталось надстроить
деньги: настраиваемая комиссия, начисление, история выплат.

Заведомо требует F49 (платежи) — без выручки нечего делить.

### F68 — Поддержка: единый инбокс обращений
Подсмотрено у Chatwoot. Обращения из лички бота и из группы — в один
список: назначение оператору, статусы, история переписки с человеком,
время реакции.

Для бизнеса блок обязательный: вопрос в личку боту сейчас не превращается
ни во что. Частично ложится на существующий лог-канал с inline-кнопками, но
нужен веб-интерфейс — в Telegram-канале список обращений не ведут.

Связано с F63: обращение должно цепляться к карточке человека, иначе
оператор каждый раз общается с незнакомцем.

### F69 — Магазин в боте: каталог, корзина, заказы
Подсмотрено у AiogramShopBot и примеров Bot Payments API. Каталог товаров,
корзина, оформление, статусы заказа, история покупок в карточке (F63).

Прямые продажи из канала без внешнего сайта. Требует F70 — для физических
товаров Stars не подходят.

### F70 — Платежи рублями и криптой (для физических товаров)
Подсмотрено у Prodamus, CryptoBot (Crypto Pay API), OxaPay.

**Дополняет F49, а не заменяет.** Разделение жёсткое и задано правилами
Telegram: цифровые товары в ботах и мини-аппах — ТОЛЬКО Stars (иначе бан),
физические товары и услуги — обычный эквайринг через Bot Payments API с
провайдером.

Провайдер подключается в @BotFather. Список провайдеров менялся, часть
российских отключалась из-за санкций — актуальность сверять на момент
подключения, а не по этому файлу.

### F71 — Воронки: движок сценариев
Подсмотрено у ManyChat, SaleBot, Typebot. Цепочки сообщений с задержками,
условиями и ветвлением по действию человека.

**Зачатки уже есть:** F45 (автоответчик и триггеры) и F46 (онбординг
новичка в личке) — это воронка без движка. Нужен слой, который позволяет
собирать такие цепочки без правки кода.

**Осознанно БЕЗ drag-n-drop конструктора.** У конкурентов визуальный
редактор — главный аргумент продажи, потому что их пользователь не
программист. Здесь пользователь — автор системы, и YAML или форма дадут тот
же результат за долю усилий. Если позже появится F27 (чтение Б), к движку
можно будет пририсовать редактор; наоборот — нельзя.

### F72 — Контент-календарь и согласование
Подсмотрено у Postiz и Publer. Сетка публикаций на месяц, drag-n-drop
переноса времени, согласование поста до публикации.

**Блокируется F37.** Согласование без ролей бессмысленно: если все под одним
паролем, согласовывать не с кем. Делать строго после ролей.

### F73 — Публичный API и вебхуки
Подсмотрено у ManyChat, Botpress, Chatwoot — их встраивают в чужие системы.

Сейчас веб-роуты обслуживают только собственную админку; подключить систему
к 1С, CRM или своему сайту без правки кода нельзя. Для автора, чей основной
профиль — интеграции (1С, ERP), это ограничение заметнее, чем звучит.

Нужны: REST наружу с ключами, вебхуки на события (пост опубликован, новый
участник, заявка рекламодателя, оплата), ограничение частоты. Проектировать
после F63 — API поверх несформированной модели данных придётся ломать.

### F74 — Mini App: витрина внутри Telegram
Подсмотрено у Telegram Web Apps API, tma.js, Mini Apps Builder, Telemetree.
Лидерборд викторин, реферальный кабинет, каталог магазина, личный кабинет
подписчика — в виде полноценного интерфейса, а не команд бота.

**Самая дорогая фича раздела: это новый фронтенд-стек, а не доработка.**
Плюс отдельная задача проверки `initData` на сервере — иначе любой сможет
выдать себя за другого пользователя.

Делать последней и только когда содержимое витрины уже существует: мини-апп
поверх пустоты показывать нечего.

### Архитектурные решения по P6 (приняты с владельцем 2026-08-15)

#### Решение 1: чтение А, но дорога в Б не закрывается
Строим под одного владельца с сотрудниками (F37), **но `tenant_id`
добавляется во все новые таблицы P6 сразу**, со значением 1 и NOT NULL.

Почему так, а не «потом добавим»: ключ арендатора на старте стоит одну
колонку, ретроспективно — миграция по всей базе плюс ревизия КАЖДОГО
запроса. Забытый фильтр в одном запросе означает показ данных чужого
арендатора; такую ошибку не ловит ни один тест, который не написан заранее.

**Что это НЕ значит.** Мы не делаем F27: ни изоляции, ни тарифов, ни
биллинга, ни Postgres. Только колонка и привычка её проставлять.
Старые таблицы F01–F51 не трогаем — их миграция станет частью F27,
если он вообще случится.

#### Решение 2: связь контуров — событийная синхронизация
Guardian публикует события о человеке, CRM (F63) их поглощает. Слияния
баз НЕ будет: изоляция контуров — единственная реальная граница
безопасности в системе (компрометация токена Engage не даёт доступа к
модерации), и она остаётся.

Владелец выбрал этот вариант вместо более дешёвого «natural key + чтение
по требованию». **Честная цена решения:** отдельный механизм доставки,
данные в CRM отстают от источника, появляется класс ошибок «событие
потерялось» — понадобятся повторы и защита от повторной обработки.

**Но выбор оказался сильнее, чем выглядел.** Тот же журнал событий
требуется деньгам: F49/F67/F69/F70 нуждаются в append-only журнале
операций (вебхук об оплате приходит дважды — без идемпотентности человек
получает доступ дважды). То есть один механизм закрывает и синхронизацию
контуров, и платёжный журнал. Строим его ОДИН раз.

Журнал — не очередь: записи не удаляются после обработки, у потребителя
свой курсор. Так новый потребитель может переиграть историю с начала.

#### Решение 3: очередь задач вместо второго планировщика
APScheduler остаётся для расписаний. Долгие операции (рассылка F64,
шаги воронок F71, повторы F55) идут через **таблицу-очередь с курсором**
и воркер в существующем процессе.

Redis и Celery НЕ вводим: устойчивость к рестарту даёт строка в БД, а не
брокер. Рассылка на 10 000 человек обязана продолжаться с места обрыва —
это свойство курсора, а не планировщика.

Один механизм на три фичи — строится один раз, до F64.

#### Решение 4: «по собеседнику» управляет токенами, а не каталогами
Семь фич P6 говорят с участником (F64, F67, F68, F69, F70, F71, F74) и по
принципу деления попадают в Engage.

**Ботов остаётся три.** Участнику нужен один `@бот`, а не четыре: четыре
токена — это четыре диалога в его списке чатов и вопрос «в каком из них
моя покупка». А вот пакет `engage/` делится на подпакеты по доменам.

#### Решение 5: F73 — это пересмотр модели угроз, а не роуты
В `webui/auth.py` записан осознанный трейдофф: CSRF-токенов нет, потому
что «нет сторонних origin» (cookie `samesite=lax` + доступ только с
localhost/VPN). **Публичный API убивает эту предпосылку.**

Значит F73 включает: ключи доступа, ограничение частоты, возврат CSRF для
UI-сессий, возможно вынос API в отдельный процесс. Это надо держать в
оценке фичи — иначе она кажется дешевле, чем есть.

### Что ещё ждёт решения владельца
1. **Маркировка против нативности** (F62) — продуктовое решение, не
   техническое. Пока не решено, кода не пишем.
2. **Нужен ли кросспостинг** (F39) — конкурировать с планировщиками на их
   поле или остаться узкими и глубокими.
3. **Когда Postgres.** При чтении А SQLite вытянет, но писателей
   становится больше: к listener, планировщику и вебу добавляются воркер
   очереди и обработчик платёжных вебхуков. Порог — не размер базы, а
   конкуренция за запись.
