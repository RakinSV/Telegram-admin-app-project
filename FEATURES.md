# Бэклог фич — Telegram Content Repost System

> Приоритет: `P0` = без этого не MVP, `P1` = сразу после MVP, `P2` = рост и
> монетизация, `P3` = идеи на будущее, не блокируют ничего.
> Каждая фича — отдельная задача для Claude Code, можно брать по порядку.

## P0 — ядро MVP

### F01 — Управление источниками
Добавление/удаление/просмотр списка отслеживаемых Telegram-каналов.
Хранение в таблице `sources` (id, channel_username, channel_title, is_active,
added_at). Интерфейс — минимум CLI-команды, в идеале — Telegram-бот команды
(`/add_source @channel`, `/list_sources`, `/remove_source @channel`).

### F02 — Telethon listener
Подключение к Telegram через Telethon (юзер-сессия), подписка на новые
сообщения в источниках из `sources`. При получении нового поста — запись в
таблицу `posts` со статусом `new`, сохранение текста, медиа (путь к файлу),
ссылки на оригинал, timestamp.

### F03 — Фильтрация по ключевым словам
Опциональные списки стоп-слов и обязательных слов на канал или глобально.
Применяется сразу при получении поста, до сохранения в очередь (либо
сохраняется со статусом `filtered_out` для прозрачности — лучше второе,
чтобы видеть, что отфильтровалось и почему).

### F04 — Дедупликация (базовая, хэш)
Хэш текста поста (нормализованный — без пробелов/регистра) для отсева точных
дублей между источниками. Простая и быстрая первая линия защиты, до
семантического дубль-чека из P1.

### F05 — Очередь постов (статус-машина)
Таблица `posts` со статусами: `new → filtered_out | duplicate | rewriting →
rewritten → pending_approval → approved | rejected → posted | failed`.
Чёткие переходы, логирование каждой смены статуса с timestamp.

### F06 — Рерайт через OpenAI-совместимое API
Клиент с конфигурируемым `base_url`/`api_key`/`model`. Промпт-шаблон
(хранится в файле/БД, не хардкод) с инструкцией на уникализацию текста
с сохранением смысла. Сохранение результата в `posts.rewritten_text`.
Логирование стоимости запроса (токены) в БД для последующего учёта расходов.

### F07 — Ручное одобрение через Telegram-бота
Бот в личке владельцу присылает рерайченный пост с inline-кнопками
✅ Одобрить / ❌ Отклонить / ✏️ Редактировать. При "Редактировать" — бот
просит прислать новый текст, заменяет `rewritten_text`. Статус меняется
соответственно нажатой кнопке.

### F08 — Публикация в группу
При статусе `approved` — публикация поста (текст + медиа, если есть) в
целевую группу через Telegram Bot API. Обновление статуса на `posted`,
сохранение `message_id` опубликованного поста и timestamp.

### F09 — Конфигурация через .env + pydantic Settings
Все параметры (telegram api_id/api_hash, session string, bot token, target
group id, openai-совместимые ключи) — через `.env`, валидация через pydantic.

### F10 — Базовое логирование и обработка ошибок
Структурированные логи всех этапов пайплайна (получен пост → отфильтрован/
прошёл → рерайчен → отправлен на модерацию → опубликован/отклонён). Retry
с экспоненциальной задержкой для сетевых вызовов (Telegram API, LLM API).

## P1 — сразу после MVP

### F11 — Авто-постинг по расписанию
APScheduler-джоба, которая публикует посты со статусом `approved` (или сразу
`rewritten`, если включён режим без модерации) по расписанию — например,
каждые N часов, либо в заданные временные слоты. Переключается флагом
`auto_post_enabled` в конфиге, не требует пересборки.

### F12 — Несколько целевых групп
Таблица `target_groups` (id, chat_id, title, is_active). Поле в `posts` или
отдельная таблица `post_targets` — какие посты в какие группы идут (может
быть all/subset). UI выбора через бот-команды или конфиг по умолчанию.

### F13 — Семантический дубль-чек (эмбеддинги)
Замена/дополнение хэш-дедупликации (F04) на эмбеддинги через тот же
OpenAI-совместимый API. Косинусное сходство между новым постом и постами
за последние N дней. Порог схожести — конфигурируемый. Хранение векторов —
можно в SQLite как BLOB или через расширение sqlite-vec, без необходимости
поднимать отдельную векторную БД на этом масштабе.

### F14 — Статистика и логи (просмотры, реакции)
Сбор `view_count`/реакций по опубликованным постам через Telegram API (если
бот — админ группы, либо период опроса через Telethon). Таблица
`post_stats` с историей по времени (для построения трендов). Команда бота
`/stats` — сводка за период.

### F15 — Стиль-профили рерайта
Несколько промпт-шаблонов под тип контента (новость/мнение/инструкция/юмор).
Либо ИИ сам классифицирует входящий пост перед рерайтом (отдельный лёгкий
запрос-классификатор), либо привязка стиля к конкретному источнику в
конфиге `sources`.

### F16 — Поиск дополнительных источников (идея пользователя)
Интеграция с Brave Search API. По ключевым словам из оригинального поста —
поиск 5-10 результатов, фильтрация на релевантность (можно через тот же
LLM — "выбери 2-3 наиболее релевантных из списка"), разделение на
русскоязычные и англоязычные. Добавление блока "Источники:" в конец
рерайченного поста со ссылками. Включается опцией на источник или глобально
(галочка "добор знаний").

### F17 — Антибан-механики
Рандомизация задержек между запросами Telethon (не молотить API без пауз).
Лимиты на количество чтений/действий в час. Конфигурируемые джиттер-интервалы.
Это must-have для стабильности, не просто "nice to have" — без этого юзер-
сессия рискует попасть под ограничения.

### F28 — Guardian настраивается по целевым группам (не глобально)
Сейчас Guardian (защита участников: капча, антиспам, антирейд, варны) жёстко
привязан к ОДНОЙ группе через `GUARDIAN_GROUP_ID` в `.env` — при этом
`target_groups` (F12) поддерживает несколько целей публикации. Если целей
несколько, Guardian реально защищает только одну из них. Нужна галочка
"использовать Guardian" на каждой `TargetGroup` в `/targets`, и Guardian
должен уметь обслуживать N групп одновременно (один бот, несколько чатов —
не N ботов). Требует ревизии схемы Guardian (`members`/`warnings`/
`banned_users` и т.д. сейчас неявно на одну группу, нужен `chat_id` как
часть ключа везде) до реализации — см. отдельный анализ перед стартом.
Найдено на аудите ведения групп (2026-07-17), запрошено пользователем явно.

## P2 — рост и монетизация

### F18 — Авто-обложки для постов
Если у поста нет медиа — генерация изображения. Два пути: (а) через
локальный ComfyUI (у пользователя уже настроен ComfyUI + ZLUDA на RX 6600 в
других проектах — можно переиспользовать инфраструктуру) или (б) через
Unsplash API по ключевым словам темы поста (бесплатно, быстрее, но не
уникально). Конфигурируемый выбор стратегии.

### F19 — Умное расписание публикаций
На основе накопленной статистики (F14) — анализ, в какое время аудитория
активнее всего (по просмотрам в первый час после публикации). Автоматический
сдвиг времени публикации под пиковые часы. Нужно minimum 2-3 недели данных
перед тем как это включать осмысленно.

### F20 — Авто-дайджест
Раз в неделю (или другой период) — джоба, которая выбирает топ-N постов по
просмотрам/реакциям за период и собирает их в один сводный пост через LLM.
Публикуется отдельно от обычного потока.

### F21 — Нативная реклама в ленте
Каждый N-й пост (конфигурируемо) — рекламный, ИИ вписывает рекламный текст
органично в формат канала по заданному брифу. Ручное добавление рекламных
брифов через бота, статистика отдельно по рекламным постам.

### F22 — Growth-трекер
Корреляция прироста подписчиков канала (нужен сбор через Telegram API или
сторонние боты-аналитики типа TGStat API) с типом/источником постов.
Отчёт "что реально растит канал".

### F23 — Веб-UI поверх системы (шаг к SaaS)
Простой веб-интерфейс (FastAPI + минимальный фронт, либо Streamlit для
быстрого старта — у пользователя уже есть опыт со Streamlit из проекта
Hedonism Wines) для управления источниками, очередью модерации, статистикой
без необходимости лезть в бота или БД напрямую. Это шаг к продукту, который
можно продавать другим владельцам каналов.

### F29 — Управление уже опубликованным постом (РЕАЛИЗОВАНО 2026-07-18)
Сейчас редактирование (`/moderation/{id}/edit`) работает только ДО публикации
(пока пост в очереди модерации). После `posted` пост неприкасаем из
админки — нельзя ни поправить текст (Bot API `edit_message_text`/
`edit_message_caption`), ни удалить (`delete_message`), ни закрепить/
открепить (`pin_chat_message`/`unpin_chat_message`). Частый сценарий
владельца канала: заметил опечатку/фактическую ошибку уже после публикации.

Реализовано веб-only (без кнопок в Telegram-боте — список из N целей на
пост неудобно рисовать inline-клавиатурой): новая таблица `PostTarget`
хранит результат публикации КАЖДОЙ цели (не только первой успешной, как
раньше), `/moderation/{id}` показывает список целей с кнопками
редактировать/удалить/закрепить-открепить по каждой отдельно.

### F30 — Модерация комментариев под постами канала (ЗАКРЫТО через F28)
Discussion-группа канала, куда Telegram зеркалит комментарии под постами —
это ОБЫЧНАЯ supergroup с точки зрения Bot API, Guardian её никак не
отличает от любой другой защищаемой группы. После F28 (Guardian настраивается
по целевым группам, не глобально) владельцу достаточно добавить
discussion-группу как цель (`/targets`) и включить галочку Guardian на ней —
капча/антиспам/варны/антирейд начинают работать над комментариями без
дополнительного кода. Отдельная реализация не нужна.

Также закрывает F36 (приветствие новых подписчиков канала) — единственный
реальный механизм приветствовать "подписавшегося" описан именно через эту
discussion-группу (см. F36 ниже), это тот же путь.

### F31 — Полный сбор метрик поста (реакции, форварды) (РЕАЛИЗОВАНО 2026-07-18)
`PostStat` в БД уже поддерживает `reaction_count`/`forward_count`, но
собирается сейчас только `view_count` (`scheduler/stats.py`). Реакции и
форварды физически доступны через Bot API/Telethon, просто не читаются.

Сбор теперь идёт по ВСЕМ целям публикации поста (через `PostTarget`, F29),
не только по первой, и суммируется в один `PostStat`-снимок на пост.

### F32 — Управление инвайт-ссылками и заявками на вступление (РЕАЛИЗОВАНО 2026-07-18)
Создание/отзыв/лимиты по инвайт-ссылкам целевых групп, одобрение/отклонение
заявок на вступление (join requests, если у группы включено подтверждение
администратором) — сейчас полностью вне системы, только руками в самом
Telegram.

Веб-страница `/invites`: создание/отзыв инвайт-ссылок (`InviteLink`),
список pending-заявок с кнопками одобрить/отклонить. Заявки также
дублируются владельцу в личку ботом с теми же кнопками (см.
`telegram/moderation_bot.py::_on_chat_join_request`).

## P3 — идеи на будущее (не блокируют разработку)

### F24 — Сравнение версий источников (РЕАЛИЗОВАНО)
Если источники на разных языках расходятся в трактовке темы — пометка поста
«есть разные версии события».

Реализовано в `enrichment/enricher.py::compare_source_versions` (промпт
`prompts/compare_sources.txt`): отдельный LLM-вызов, срабатывает ТОЛЬКО когда в
доборе (F16) нашлись источники обоих языков и включена настройка
`version_comparison_enabled` (по умолчанию выключена — это лишний платный
вызов). При расхождении в начало блока источников добавляется строка
«⚠️ Разные версии события: …».

### F25 — Авто-реакция на жалобы/негатив (РЕАЛИЗОВАНО)
Мониторинг негативных реакций на опубликованный пост, уведомление при
превышении порога, опциональное авто-удаление.

Реализовано в `scheduler/stats.py`: подсчёт негативных реакций при опросе
статистики, порог и авто-удаление настраиваются в /settings → «Реакция на
негатив», есть почасовой лимит авто-удалений (`max_auto_deletes_per_hour`),
чтобы всплеск негатива не выкосил ленту.

### F26 — Ротация между несколькими Telethon-сессиями (РЕАЛИЗОВАНО)
Балансировка чтения между несколькими юзер-сессиями — масштабирование числа
источников без риска для одного аккаунта.

Реализовано в `telegram/listener.py`: дополнительные клиенты поднимаются по
сохранённым сессиям (`TelethonSession`, страница /telethon-sessions), источники
распределяются между ними по кругу, у КАЖДОГО аккаунта свой почасовой лимит
«тяжёлых» действий (F17/F26). Общий прокси на все клиенты (см. `proxy.py`).

### F27 — SaaS multi-tenant архитектура
Полноценный переход от "система для одного владельца" к multi-tenant
продукту с отдельными аккаунтами, биллингом, изоляцией данных между
клиентами. Это отдельный по объёму проект поверх текущего ядра, не задача
на ближайшие месяцы.

### F33 — Опросы (polls) в ленте (РЕАЛИЗОВАНО 2026-07-18)
Публикация `send_poll` как отдельный тип поста или довесок к обычному —
вовлечение аудитории без необходимости писать комментарий.

Реализовано как новый `PostKind.POLL`: страница `/polls` создаёт пост-опрос
(вопрос + 2-10 вариантов), дальше он идёт по ТОМУ ЖЕ пайплайну модерации/
публикации, что и обычный пост — `publish_post` шлёт его через
`bot.send_poll`, не `send_message`.

### F34 — Inline-кнопки на опубликованном посте (РЕАЛИЗОВАНО 2026-07-18)
Ссылка на сайт-первоисточник, "читать полностью", кнопки шаринга — сейчас
посты уходят как голый текст+медиа без разметки клавиатуры.

Реализована узкая версия: настраиваемая (`/settings`) inline-кнопка со
ссылкой на `source_link` — показывается только когда включено И у поста
реально есть на что ссылаться (AD/DIGEST/POLL — никогда). Кнопки
шаринга/произвольные не реализованы — не было конкретного запроса, добавить
несложно по образцу при необходимости.

### F35 — Ручной учёт рекламного дохода (РЕАЛИЗОВАНО 2026-07-18, СУЖЕННЫЙ СКОУП)
F21 (нативная реклама) даёт только бриф → вписывание в ленту. Нет ни
интеграции с биржами (Telega.in и т.п.), ни учёта фактического дохода от
рекламных постов — этого требует полноценная монетизация, не только
публикация.

Решено с пользователем 2026-07-18: настоящей интеграции с биржей не будет
(нет партнёрского API-доступа ни к одной конкретной) — реализован РУЧНОЙ
журнал (`AdRevenue`): кто заплатил, сколько, когда, опционально привязка к
брифу. Страница `/ads` показывает итог по каждой валюте (без конвертации).

### F36 — Приветственные сообщения новым подписчикам канала (ЗАКРЫТО через F30)
Bot API физически не даёт события "на канал подписались" — у ботов такого
апдейта нет в принципе, ни при каких правах. Единственный реальный путь —
привязанная к каналу discussion-группа: подписчики, оставляющие первый
комментарий, вступают именно в неё, и вот ТАМ Guardian уже умеет
приветствовать/капчить (см. F30, теперь применимо к любой защищаемой группе
после F28). Отдельной фичи не будет — решено с пользователем 2026-07-18.

### F37 — Несколько администраторов веб-панели с разными правами (ПРОПУЩЕНО)
Сейчас один пароль на всю систему (`admin_users` — таблица физически на
одну строку). Актуально, если управлением занимается не один человек.

Решено с пользователем 2026-07-18: пропустить целиком для этого захода —
однопользовательский инструмент, ролевая модель не нужна прямо сейчас.

### F38 — Экспорт/бэкап контента канала (РЕАЛИЗОВАНО 2026-07-18)
`backup.py` уже бэкапит БД (посты, настройки), но нет экспорта именно
содержимого в независимый от системы формат (например, для передачи новому
владельцу канала или архива для комплаенса).

Страница `/export`: выгрузка всех опубликованных постов (текст, ссылка на
источник, цели публикации, последние метрики) в JSON или CSV, с
опциональным фильтром по дате публикации.

### F39 — Кросспостинг на другие платформы
Публикация того же (или адаптированного) контента в VK/Instagram и т.п. —
не было в изначальном скоупе проекта, но частая задача владельцев каналов,
растящих присутствие сразу на нескольких площадках.

### F40 — Редакция из двух агентов: профессиональный рерайт (РЕАЛИЗОВАНО 2026-08-01)
Раньше рерайт был «в один присест»: модель писала пост начисто, никто его не
правил — отсюда слабый, местами выдуманный текст. Теперь тот же клиент играет
ДВЕ роли (`rewriter/editorial.py`):

1. **Журналист** пишет черновик по источникам (персона усилена: журналист с
   20-летним опытом).
2. **Редактор-фактчекер** сверяет черновик с источниками (исходный пост +
   статья по ссылке), пишет пронумерованные замечания и вердикт OK/ПРАВИТЬ,
   помечает спорные факты на веб-сверку.
3. **Веб-сверка** помеченных фактов через тот же поиск, что F16 (SearXNG/
   Brave); находки идут журналисту.
4. **Журналист переписывает** по замечаниям и находкам. Цикл — до вердикта OK
   или до `editorial_max_rounds`.

Замечания редактора сохраняются на варианте (`PostRewriteVariant.editorial_notes`,
миграция 0023) и показываются при модерации. По умолчанию ВКЛ, 1 раунд; всё —
настройками в /settings → «Редакция из двух агентов». Дороже по токенам: 1 раунд
= 3 вызова LLM на вариант, поэтому под выключателем. 402/ошибка баланса на любом
шаге останавливает пачку (посты остаются `new`); прочие сбои рецензии/правки не
теряют хороший черновик.

## P4 — Вовлечение аудитории: боты-помощники админа (F41–F49)

Запрос владельца 2026-08-01: нужны дополнительные обслуживающие боты —
геймификация, приглашения с указанием источника рекламы, конкурсы, «и что там
ещё надо админам групп». Ниже — результат разбора, что реально нужно и что
физически позволяет Telegram Bot API.

### Архитектурное решение: куда что класть

Три процесса вместо двух, с чётким разделением по СОБЕСЕДНИКУ:

| Процесс | С кем говорит | Зона ответственности |
|---|---|---|
| Репост-бот (есть) | владелец | публикация, модерация контента |
| Guardian (есть) | группа | защита: капча, антиспам, варны, антирейд |
| **Engage (новый)** | **участники** | квизы, конкурсы, рефералы, предложка, онбординг |

**Итого три бота.** Разделены по СОБЕСЕДНИКУ, а не по фичам — это и есть
причина, по которой третий бот действительно нужен, а не «ещё один процесс ради
процесса»:

- Репост-бот — приватный инструмент владельца (кнопки одобрения постов, статистика).
- Guardian — «полицейский» в группе, участники с ним не разговаривают.
- Engage — публичный, дружелюбный: участники пишут ЕМУ в личку, deep-link
  рефералки ведёт на НЕГО, он же ведёт квизы и конкурсы. Смешивать его с
  «ботом владельца» — плохой UX (подписчик видит чужие админ-кнопки) и лишняя
  поверхность атаки.

**Важно: Engage НЕ читает поток сообщений группы.** Ему это не нужно — квиз
работает по схеме «бот спросил → участник нажал кнопку → `poll_answer`».
Значит, не нужен privacy mode off, не нужно дублировать трафик Guardian'а и не
растут риски по лимитам Telegram. Это следствие правильно выбранной механики
(см. F43): если бы очки давались за сообщения, второй читатель потока был бы
неизбежен.

### Что Telegram реально позволяет (сверено с Bot API)

- **`ChatMemberUpdated.invite_link`** и **`ChatJoinRequest.invite_link`** — при
  вступлении Telegram САМ сообщает, по какой ссылке пришёл человек. **Эти данные
  нам уже приходят в существующие хендлеры, но мы их не сохраняем** — отсюда F41,
  самая дешёвая и самая полезная фича блока.
- **Deep-link `t.me/<bot>?start=<payload>`** (payload до 64 символов) — основа
  реферальной программы: по нему бот узнаёт, кто пригласил.
- **`getChatMember(chat_id, user_id)`** — проверка «подписан ли» для условий
  конкурса. Требует, чтобы бот был админом в проверяемом чате.
- **`sendDice`** — нативный рандом Telegram (кубик/дартс), годится для
  наглядного публичного розыгрыша «на глазах у зрителей».
- **Ограничение:** в КАНАЛАХ у постов нет авторов-участников — бот не видит, кто
  что написал. Геймификация по активности работает только в ГРУППАХ, включая
  discussion-группу канала (что для канала и есть рабочий вариант).
- **Нет события «подписался на канал»** — у ботов такого апдейта не существует
  (уже упиралось в F36). Прирост канала считаем по `getChatMemberCount`, а
  поимённо — только по вступлениям в группу.

### F41 — Атрибуция подписчиков: откуда пришёл (P1, дёшево и сразу ценно)
Продолжение F32. Сейчас инвайт-ссылки создаются и отзываются, но **никто не
знает, какая из них сколько привела** — данные от Telegram выбрасываются.

Сохранять `invite_link` при вступлении (`chat_member`) и в заявке
(`chat_join_request`) → поле в `JoinRequestRecord` + новая таблица
`MemberOrigin` (chat_id, user_id, invite_link_id, joined_at, left_at).
На `/invites` — колонки «пришло / осталось сейчас / отвалилось / retention 7д и
30д». Плюс поле «стоимость размещения» у ссылки → **CPA, цена подписчика**.

Это замыкает контур с F35 (учёт рекламного дохода) с другой стороны: F35 — что
заработали на рекламе у себя, F41 — что потратили на рекламу себя и что это
принесло.

### F42 — Реферальная программа для участников (P2)
Участник пишет боту Engage → получает персональную ссылку
`t.me/<bot>?start=ref_<user_id>` (или персональную инвайт-ссылку группы) →
система считает, кого он привёл и кто из них остался. Лидерборд рефереров,
награды за пороги (N приглашённых → роль/бейдж/приз). Защита от накрутки:
приглашённый засчитывается только если прожил в группе > N дней и написал хотя
бы одно сообщение.

### F43 — Геймификация: контент → вопрос → очки (P2)
**Механика владельца (уточнено 2026-08-01):** бот САМ выдаёт контент, а через
время задаёт по нему вопрос. Ответил верно — очки.

Это принципиально лучше «очков за сообщения»: те превращаются в ферму флуда
(люди пишут «+», «ок», чтобы набить счётчик), а здесь очки даются за то, что
человек реально прочитал материал. И механика самодостаточна: не требует, чтобы
в группе кто-то что-то писал — бот сам создаёт повод.

**Почему это ложится на нашу систему почти без работы:** у нас уже есть полный
текст статьи (trafilatura, F16), готовый пост и редактор-фактчекер (F40),
который эти факты проверил. Составить из проверенного материала вопрос с
вариантами ответа — ОДИН дополнительный LLM-вызов. Вопрос гарантированно
основан на реальном тексте, а не на выдумке модели.

Схема:
1. Пост опубликован обычным пайплайном.
2. **Составитель квиза** (новая LLM-роль) делает из статьи вопрос + 3–4 варианта
   ответа, один верный, плюс короткое пояснение со ссылкой на источник.
3. Через настраиваемую паузу бот Engage публикует вопрос в группу как
   **quiz-poll** (`sendPoll(type="quiz", correct_option_id=...)`).
4. Очки за правильный ответ, бонус за скорость и за серию дней.
5. Уровни/бейджи, `/me`, `/top` (день/неделя/месяц), авто-пост лидерборда.

**Почему quiz-poll, а не свободный ответ:** Telegram нативно поддерживает
викторину — сам проверяет правильность, показывает верный вариант с пояснением
и не даёт переголосовать. Это ноль LLM-вызовов на проверку ответов и ноль
споров «я вообще-то это и имел в виду». Свободные ответы с LLM-проверкой —
возможное расширение потом, но дороже и спорнее.

Очки начисляются также за приведённого реферала (F42) и участие в конкурсе
(F44). Настраивается на чат, выключается одной галочкой.

**Ограничение:** публиковать вопрос и видеть ответы бот может только в ГРУППЕ
(в канале нет участников-авторов) — для канала это его discussion-группа.

### F44 — Конкурсы и розыгрыши (P2)
Создание конкурса в веб-админке: период, приз, число победителей, **условия
участия** (подписан на канал(ы) — проверка `getChatMember`; состоит в группе;
минимум N очков F43; привёл N рефералов F42). Участие — кнопкой под постом
конкурса. По окончании: проверка условий у всех записавшихся, честный розыгрыш
и автообъявление победителей с упоминанием.

**Прозрачность розыгрыша** (иначе аудитория не верит): seed фиксируется заранее
и публикуется вместе с алгоритмом, чтобы любой мог перепроверить результат;
опционально — публичный `sendDice` для наглядности. Полный протокол розыгрыша
сохраняется в БД.

### F45 — Автоответчик и триггеры по ключевым словам (P3)
Частые вопросы («как купить», «где правила», «когда стрим») → авто-ответ по
ключевым словам с антиспам-защитой (не чаще раза в N минут на чат, не отвечать
самому себе). Снимает с админа рутину. Технически — ложится в Guardian, он уже
разбирает каждое сообщение по фильтрам.

### F46 — Онбординг новичка в личке (P3)
Guardian уже капчит и приветствует В ГРУППЕ. F46 — следующий шаг: Engage пишет
новичку В ЛИЧКУ (если тот стартовал бота) короткий онбординг — правила, что тут
есть, полезные ссылки, кнопка «показать топ участников». Конверсия «вступил →
остался» заметно выше, когда человека встретили.

### F47 — Предложка: посты от подписчиков (UGC) (P3)
Участник шлёт пост боту Engage → тот кладёт его **в ту же очередь модерации**,
что и рерайты (`PostKind.UGC`, статус `rewritten`) → владелец одобряет в боте
или веб-админке → публикуется с указанием автора. Красиво переиспользует весь
существующий пайплайн модерации/публикации: новый только источник поступления.

### F48 — Служебная гигиена группы (P1, мелочь, но хотят все)
Пакет мелких, но раздражающих-в-отсутствие вещей:
- авто-удаление служебных сообщений («вошёл в группу», «закрепил сообщение»);
- ночной режим: авто-включение slow mode / закрытие группы на ночь и открытие
  утром (у Guardian уже есть «тихие часы» — расширить до действий);
- напоминание правил по расписанию;
- авто-закрепление важного поста после публикации.

### F49 — Платный доступ и подписка (идея, не задача)
Монетизация закрытого канала: оплата через Telegram Stars → автовыдача
инвайт-ссылки с ограничением, авто-кик по окончании подписки, продление.
Отдельный крупный кусок с платёжным контуром и юридическими вопросами —
записано, чтобы не потерялось, но не в ближайшую очередь.

### Что НЕ вошло и почему
- **Приветствие подписчиков канала поимённо** — Bot API физически не даёт
  события подписки на канал (см. F36, закрыто через discussion-группу).
- **Учёт кросс-промо с другими каналами** — по сути ручной журнал, покрывается
  F35 (журнал дохода) и F41 (атрибуция) без отдельной фичи.
- **Собственный анти-бот-скоринг** — уже есть в Guardian (G10 гибридный режим +
  G15 анализ профиля).
